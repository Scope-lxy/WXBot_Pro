# 微信 UI 主动轮询重构备选方案

## 文档状态

这是未来重构备选，不是当前生产规则。

当前生产方案继续使用 wxautox4 的 `AddListenChat + callback` 监听。现有 UI 锁和 watchdog 处理不改变消息入口。

只有完成本文列出的真实微信高负载 A/B 验证，并证明消息实时性、图片语音、去重和恢复均不退化后，才允许考虑切换到主动轮询。

## 为什么保留这个方案

当前模式相当于“wxauto 看到新消息后主动敲门”。好处是实时、沿用时间长；代价是 wxauto 的监听线程会接触微信 UI，并可能在持有内核全局锁时进入项目回调。

主动轮询相当于“唯一 UI owner 按固定节奏逐个窗口巡查”。这样所有微信 UI 调用都由 owner 发起，线程归属更直观，也不再需要处理“监听线程持锁、回调等待 owner”的特殊交接。

它解决的是架构复杂度，不是当前必须改的故障；切换会改变消息入口和调度节奏，必须单独验证。

## wxautox4 接口依据

官网文档确认：

- `AddListenChat` 会把目标聊天独立成 `Chat` 子窗口，并以 `(Message, Chat)` 调用 callback。
- `StartListening / StopListening` 控制后台监听。
- `GetNextNewMessage` 从主窗口取得下一批新消息，官方明确提示其 callback 内不要发送消息。

当前已安装并固定的 `wxautox4==41.1.1.post1` 还提供：

- `WeChat(..., start_listener=False)`；必须显式传 `False`，不能依赖不同文档或类型标注中的默认值。
- `Chat.GetNewMessage()`；返回该独立聊天窗口的新消息列表。

后两项必须在每次内核升级时重新核对签名和实机行为，不能只根据本文件继续使用。

## 目标运行方式

1. owner 用 `WeChat(start_listener=False)` 创建客户端，整个生命周期不调用 `StartListening()`。
2. 仍用 `AddListenChat` 创建和维护独立 `Chat` 窗口，但传入的 callback 不承担生产收消息；必须实测确认后台监听未启动时不会自行调用 callback。
3. owner 按小批次轮转各个 `Chat`，调用 `Chat.GetNewMessage()`；单个繁忙会话不能长期占满 owner。
4. 原始 `Chat / Message` 始终留在 owner 内。owner 先生成纯数据消息快照并把图片、引用等占位事实写入 SQLite，落库成功后才能用原 `Message` 下载，再用本地路径补充原事件。
5. 纯数据批次离开 owner 后，继续走现有 `InboundCoordinator`、消息合并、AI 回复和投递链路，不重写业务逻辑。
6. `GetNextNewMessage()`只用于启动积压、尚未建立子窗口的会话和窗口失效兜底，不作为稳定期每轮主扫描方式。

## 必须保持的边界

- `message_store.sqlite3` 继续是消息、会话版本、回复和投递状态的唯一真源。
- 发送、转发、素材读取、关系扫描、通讯录恢复和主动收消息共享同一个 owner 队列。
- 任何 `Message` 都不能离开 owner；业务线程只能接收纯数据快照和本地文件路径。
- 图片、引用和语音必须先有持久化消息事实，再做下载或转写。
- 无消息是正常空批次；空结果不能生成“不支持会话”错误。
- 结果未知的发送仍标记 `uncertain`，禁止自动重发。
- 通讯录子进程和 300 秒硬超时边界不变。

## 主要风险

| 风险 | 需要验证的结果 |
| --- | --- |
| 实时性下降 | 安静期和高负载下，从微信出现消息到 SQLite 落库、开始回复的延迟均可接受。 |
| 忙会话挤占 | 大群连续来消息时，私聊和其他群仍能在目标时间内被轮询。 |
| 图片 / 引用丢失 | 原消息不跨线程的前提下，占位落库、下载、补路径和识别都完整。 |
| 语音重复或漏转写 | 轮询重复返回、窗口重建和进程恢复后仍只产生一个消息事实。 |
| 窗口数量增长 | 多个独立窗口的创建、关闭、微信重启恢复和句柄失效处理稳定。 |
| 扫描与发送互相拖延 | 收消息批次足够短，发送和资料任务不会长期饿死；发送高峰也不会造成明显漏读。 |
| 内核升级改变语义 | 每次升级重新验证 `start_listener=False`、`AddListenChat` 和 `GetNewMessage()`，失败即保持现方案。 |

## 建议的 A/B 验证门槛

先做独立实验开关，不直接替换生产默认值。相同微信版本、相同监听名单下分别运行现方案和主动轮询方案，至少覆盖：

- 私聊、群聊、@、连续多条、多人同时发送。
- 文本、图片、引用图片、语音、文件和机器人自身回声。
- 发送与收消息同时发生，素材转发和关系扫描期间来消息。
- 通讯录批次前、中、后，以及微信窗口重建和机器人进程重启。
- 两小时以上高负载运行，检查漏消息、重复消息、错会话、错误下载、排队延迟和 UI 卡死。

采用条件不是“没有自动重启”这一项，而是以上事实完整性和用户体验均不差于当前方案。任何一项无法证明，就继续使用 `AddListenChat + callback`。

## 与当前生产方案的区别

| 当前生产方案 | 主动轮询重构 |
| --- | --- |
| 保留 wxauto 后台监听和 callback | 停止后台监听，由 owner 主动巡查 |
| 保持现有消息入口、锁交接和 watchdog 边界 | 改变消息入口、实时性和窗口调度 |
| 不动消息落库、AI、发送和恢复主链 | 必须重新验证全部入站消息类型和恢复流程 |
| 继续按现有回归和实机规则维护 | 只能在独立实验和真实微信 A/B 后决定是否采用 |
