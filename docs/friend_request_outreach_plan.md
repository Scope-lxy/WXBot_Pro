# 好友申请开发方案

## 目标

在【新好友】页面新增一个独立 L1 模块：`好友申请`。

第一期用于把“删除我的人”这类已打标签的联系人重新发起好友申请；但模块不要绑定死“删除我的人”。这里把它抽象成一套通用的好友申请能力：

- 来源：从哪里拿到待添加对象
- 候选人：经过清洗、去重和风控过滤后的目标
- 文案规则：给不同目标选择什么附加消息
- 发送器：真正调用微信接口发出好友申请
- 执行记录：每天限额、失败重试、跳过原因和可追踪结果

这样后续扩展“批量发送好友申请”“自动添加群内好友”时，只需要新增来源适配器或发送器，不需要重做 UI 和调度。

## 功能定位

页面位置：

- 一级导航仍放在【新好友】
- 【新好友】页内新增 L1 模块 `好友申请`
- 与现有软件常用结构一致：顶部胶囊状态、左侧卡片、右侧详情/设置

建议文案：

- L1 标题：`好友申请`
- 模块说明：`从标签、名单或群成员生成候选人，按限额和时间段自动发送好友申请`
- 第一期来源名称：`通讯录标签`
- 第一期预置标签：`删除我的人`

不要把 UI 文案写成“删除我的人加回”。用户能感知到的功能可以是“把删除我的人加回来”，但产品结构要保持可扩展。

## 第一期范围

第一期只做“标签来源”：

- 支持选择一个或多个本地通讯录/微信标签
- 默认建议标签为 `删除我的人`
- 读取标签下的联系人，逐个发起好友申请
- 对 `删除我的人` 这类关系恢复场景，默认不走搜索添加，而是进入该联系人会话，点击会话里的 `发送朋友验证`
- 每天最多发送 N 次申请
- 每次申请之间有基础间隔和随机抖动
- 只在允许的时间段内发送
- 附加文案按标签匹配，支持一个标签配置多条文案
- 文案可以随机使用，也可以按顺序轮换

不建议第一期做：

- 自动全量扫描群成员并添加
- 从外部 Excel/CSV 批量导入
- 多微信号并发跑同一批目标
- 对微信风控做强绕过

这些可以作为后续来源或策略扩展。

## 用户流程

1. 用户进入【新好友】页，切到 `好友申请` 模块。
2. 顶部胶囊看到今天申请数、待申请数、成功数、失败数、下次执行时间。
3. 右侧设置来源和发送策略：
   - 来源类型：第一期为 `通讯录标签`
   - 加哪些标签的人：多选标签，默认可选 `删除我的人`
   - 每天最多申请：例如 20
   - 申请间隔：例如 30 分钟
   - 随机抖动：默认自动，例如 +/- 10%，也可做高级项
   - 可发送时间段：例如 09:30-12:00、14:00-21:30
   - 申请后权限：朋友圈 / 仅聊天
   - 成功后标签：可选，沿用已成熟标签选择器
   - 成功后备注：可选，复用新好友备注规则或留空
4. 左侧添加附加文案规则：
   - 规则按标签匹配
   - 一个规则可以选多个标签
   - 一个标签可以有多条附加文案
   - 命中多条时按随机或顺序使用
   - 没命中时使用默认文案
5. 用户开启任务后，系统按候选队列逐个发送好友申请。
6. 每次执行后写入记录，UI 展示最近结果和失败原因。

## UI 结构

### 顶部胶囊

建议胶囊：

- `开关`：已开启 / 已关闭
- `今日申请`：已发送 / 每日上限
- `待申请`：候选队列中剩余人数
- `成功`：今天成功发出申请的人数
- `失败`：今天失败或被跳过的人数
- `下次执行`：具体时间或“等待时间段”

### 左侧卡片：申请文案

左侧用于维护“按标签匹配的附加文案”，样式参考【关键词回复】的规则列表。

建议字段：

- 匹配标签：多选标签
- 使用方式：随机 / 顺序
- 附加文案列表：不设上限，建议前端不硬限制，后端只做单条长度校验
- 默认文案：没有任何标签规则命中时使用
- 状态：启用 / 停用

匹配规则：

- 候选人命中多个标签时，按规则列表顺序找第一条可用规则
- 同一规则内多条文案按 `random` 或 `round_robin` 选取
- 如果没有命中文案规则，使用默认文案
- 如果默认文案也为空，可以允许空附加消息，但 UI 需要提示风险

文案变量建议预留：

- `{昵称}`
- `{备注}`
- `{标签}`
- `{微信号}`

第一期可以先只保存变量原文，不做复杂模板；实现时再统一替换。

### 右侧卡片：来源与发送设置

右侧用于维护具体执行参数。

建议字段：

- 启用好友申请：开关
- 来源类型：`通讯录标签`
- 目标标签：成熟标签选择器，多选
- 每天最多申请：默认 20，建议范围 1-200
- 基础申请间隔：默认 30 分钟，建议最小 5 分钟
- 随机抖动：默认 `自动`，实际按基础间隔 +/- 10% 计算，至少 +/- 1 分钟
- 可发送时间段：支持多个时间段
- 申请权限：朋友圈 / 仅聊天
- 发送成功后标签：可选
- 发送成功后是否移出来源标签：默认关闭；对 `删除我的人` 建议不要自动移除，等对方通过后再由关系扫描恢复
- 失败重试：默认不自动重试；后续可做 1-3 次
- 黑名单/排除标签：预留，避免误加高风险标签

## 来源模型

不要在代码里写死“删除我的人”。建议统一来源协议：

```json
{
  "source_id": "tag:deleted_me",
  "source_type": "contact_tags",
  "name": "删除我的人",
  "settings": {
    "include_tags": ["删除我的人"],
    "exclude_tags": []
  }
}
```

后续可扩展来源：

- `contact_tags`：通讯录标签来源，第一期实现
- `manual_list`：手动输入微信号/手机号/昵称
- `file_import`：Excel/CSV 导入
- `group_members`：群成员来源
- `message_cards`：名片消息来源
- `search_keywords`：搜索关键词来源

统一候选人结构：

```json
{
  "candidate_id": "contact:wxid_xxx",
  "source_id": "tag:deleted_me",
  "source_type": "contact_tags",
  "display_name": "张三",
  "remark": "张三-老客户",
  "nickname": "张三",
  "wechat_id": "wxid_xxx",
  "phone": "",
  "tags": ["删除我的人", "老客户"],
  "search_keyword": "wxid_xxx",
  "conversation_keyword": "张三-老客户",
  "sender_kind": "conversation_verify",
  "status": "pending",
  "last_result": "",
  "created_at": "2026-06-11T10:00:00",
  "updated_at": "2026-06-11T10:00:00"
}
```

字段说明：

- `search_keyword`：给 `wx.AddNewFriend(keywords=...)` 使用，优先级为微信号、手机号、备注/昵称
- `conversation_keyword`：给 `wx.ChatWith(...)` 使用，用于打开已有会话
- `sender_kind`：决定发送器；`删除我的人` 默认 `conversation_verify`，普通名单/搜索来源默认 `search`
- `tags`：用于文案匹配和后续状态展示
- `status`：`pending / sent / skipped / failed / accepted / archived`

## 发送器模型

发送器不要和来源绑死。建议拆为：

- `conversation_verify_sender`：打开已有会话，点击 `发送朋友验证` 呼出申请窗口
- `search_add_friend_sender`：通过搜索关键词发起好友申请
- `message_add_friend_sender`：通过消息对象发起好友申请
- `group_member_add_friend_sender`：后续群成员来源专用，可以内部落到 `message_add_friend_sender` 或 UI 点击路径

第一期 `删除我的人` 候选发送器设计：

```python
wx.ChatWith(conversation_keyword, exact=True)
# 在当前会话中定位并点击“发送朋友验证”
# 弹出“申请添加朋友”窗口后，填写附加消息、备注、标签和朋友权限，再确认
```

这个路径对应用户在微信会话里看到的系统提示：

`对方开启了朋友验证，你还不是他（她）朋友。请先发送朋友验证请求，对方验证通过后，才能聊天。发送朋友验证`

这里的关键不是搜索手机号/微信号，而是复用已有会话里的蓝色 `发送朋友验证` 入口。

当前状态：**本机单人链路已验证，批量自动化仍需灰度验证**。

- 2026-06-11 已在本机用单个测试目标验证：`wx.ChatWith(...)` 打开会话后，点击会话底部蓝色 `发送朋友验证`，可呼出 `申请添加朋友` 窗口，并可通过 `AddFriendsWnd.send(...)` 填写中文附加消息、备注和朋友圈权限后提交
- 该验证只证明当前机器、当前微信版本、当前窗口尺寸下的单人链路可行
- 接入自动任务前仍需要做多目标、不同窗口遮挡/缩放、不同会话长度、无入口/已恢复/同名联系人等灰度验证
- UI 上如果先做页面，应把该发送器标为“已单人验证，批量谨慎开启”，默认仍不可自动批量发送

#### `发送朋友验证` 定位策略

正式实现不要使用固定屏幕坐标。不同设备、分辨率、DPI、微信窗口尺寸和消息换行都会导致固定坐标失效。

建议按下面优先级定位：

1. UIA 子控件定位
   - 优先在当前会话消息控件下查找 Name 包含 `发送朋友验证` 的 `HyperlinkControl` / `TextControl`
   - 如果微信版本把蓝色文字暴露为独立可点击控件，直接调用该控件的 `Click`
   - 本机 2026-06-11 复测结果：当前微信版本未把 `发送朋友验证` 暴露为独立子控件，系统消息控件 `children_count=0`

2. UIA 文本范围定位
   - 如果系统消息控件支持 `TextPattern`，从完整系统消息中查找 `发送朋友验证` 子串
   - 读取该文本范围的 BoundingRectangle，并在范围内选择带轻微偏移的点击点
   - 如果文本范围返回多个矩形，说明链接发生了换行，需要从每个可点击片段里选择一个片段点击
   - 这是最理想的跨分辨率方案，因为点击点来自真实文字范围，不依赖截图
   - 本机 2026-06-11 复测结果：当前微信版本的系统消息控件不支持可用 `TextPattern`，暂时不能走文本范围方案

3. 消息控件动态区域定位
   - 如果微信只暴露一整个 `ListItemControl`，先用 `wx.GetAllMessage()` 找到包含 `开启了朋友验证` 和 `发送朋友验证` 的 `SystemMessage`
   - 使用该消息控件的 `BoundingRectangle`，在控件内部定位尾部链接区域
   - 点击点必须基于当前控件矩形动态计算，不能写死全屏坐标，也不要固定点击几何中心
   - 必须支持链接换行：`发送朋友验证` 可能被拆成 `发送朋` + `友验证` 两行，不能假设蓝色文字是一条连续水平区域

4. 截图/像素识别兜底
   - 只在前 3 种方式都不可用时启用
   - 识别范围必须限制在当前系统消息控件的 BoundingRectangle 内
   - 只识别该区域里的蓝色文字有效区域，不扫描整屏
   - 蓝色文字可能形成多个连通区域或多行区域，需要按行/连通块聚类，选择任意一个足够大的蓝色文字块点击，而不是取所有蓝色像素的整体中心
   - 在当前微信版本下，由于 UIA 子控件和 TextPattern 都不可用，正式实现可以把“系统消息控件矩形 + 局部蓝色文字聚类”作为 `conversation_verify_sender` 的默认定位方式，但必须只截取消息控件局部区域

当前推荐实现：

- 第一层：`wx.GetAllMessage()` 找到目标会话中最新的朋友验证 `SystemMessage`
- 第二层：读取该消息控件的 `BoundingRectangle`
- 第三层：在这个矩形内做局部蓝色文字聚类，得到一个或多个蓝色片段
- 第四层：选择位于消息尾部、宽度至少约 3 个中文字、可见的蓝色片段
- 第五层：在该片段内部生成带偏移的点击点
- 这个方案不依赖全屏固定坐标，也不依赖完整窗口截图；它依赖当前消息控件的实时位置，因此能适配不同分辨率和窗口位置

点击偏移策略：

- 不要每次点击控件或文字的绝对中心点
- 在目标文字片段的有效矩形内生成小范围随机偏移，例如 X 方向在片段宽度的 35%-70% 区间，Y 方向在片段高度的 40%-65% 区间
- 偏移必须被限制在目标有效矩形内，不能偏出到系统消息灰字、聊天输入框或其他按钮
- 同一目标重试时也要重新计算偏移，避免连续两次点击同一点
- 偏移幅度要小而稳定，优先模拟人在文字区域内点不同位置，不要做大范围随机坐标
- 所有点击都要记录来源矩形、实际点击点和定位方式，方便排查误点

链接换行处理：

- 不要把整条系统消息的 BoundingRectangle 当成链接区域
- `发送朋友验证` 可能出现在一行，也可能因为窗口宽度被拆成两行，例如第一行 `发送朋`，第二行 `友验证`
- 如果 UIA 能返回多个文本矩形，优先点击面积合适、可见且位于消息尾部的其中一个矩形
- 如果只能做图像兜底，需要先按蓝色像素的 Y 轴聚类成行，再按 X 轴聚类成片段
- 点击时选择某一个蓝色片段内部点，不要对多个换行片段求整体中心；整体中心可能落在两行之间的空白处
- 如果只识别到 `友验证` 这一行，也可以点击，因为它仍属于同一个蓝色链接
- 正常换行后最小可点击片段也应至少有 3 个中文字宽度，例如 `友验证`；不要因为片段不是完整 `发送朋友验证` 就判失败
- 只有当蓝色片段明显小于 3 个中文字宽度、靠近输入框边界或被遮挡时，才判定为识别不完整并跳过目标，不做盲点

折行片段选择规则：

- `发` / `送朋友验证`：选择第二行 `送朋友验证`
- `发送` / `朋友验证`：选择第二行 `朋友验证`
- `发送朋` / `友验证`：两段都可点，优先选择第二行 `友验证`
- `发送朋友` / `验证`：第二行不足 3 个字，选择第一行 `发送朋友`
- `发送朋友验` / `证`：第二行不足 3 个字，选择第一行 `发送朋友验`
- 完整一行 `发送朋友验证`：选择该行内部带偏移点击
- 选择策略可以概括为：优先选择宽度至少约 3 个中文字的片段；片段宽度接近时优先选择更靠后的行；如果下方尾段不足 3 个字，则选择上方更宽片段

遮挡和重试处理：

- 每个候选执行前都要先恢复并置顶微信窗口
- 每次点击 `发送朋友验证` 前，再次置顶微信窗口，避免 Codex、浏览器、文件夹或其他窗口遮住链接区域
- 如果第一次没有找到系统消息、蓝色片段或申请窗口，先重新置顶微信窗口并重新读取会话，而不是立刻判失败
- 建议最多重试 2 次；两次都失败才记录失败原因并跳过目标
- 重试时必须重新获取 `SystemMessage.control.BoundingRectangle` 和蓝色片段，不复用上一次坐标
- 如果置顶后仍识别不到蓝色片段，说明入口可能不存在、会话已恢复、窗口缩放异常或被其他系统层遮挡，应跳过，不做盲点

```python
)
```

根据 wxauto 文档，`AddNewFriend` 支持通过昵称、微信号、手机号等关键词搜索添加好友，并可传附加消息、备注、标签、朋友圈权限和搜索超时。

补充发送器：

```python
msg.add_friend(
    addmsg=addmsg,
    remark=remark,
    tags=tags,
    permission=permission,
)
```

根据 wxauto 文档，`Message.add_friend` 适用于群聊中尚未添加的成员，或可添加好友的名片/消息场景。它不应该作为“删除我的人”标签来源的主路径，但后续“自动添加群内好友”会用到。

### 会话验证发送器的后续验证

这个能力已经完成一次单人实机验证，但还不能直接等同于批量稳定。后续需要按下面流程补充灰度验证。

验证前置条件：

- 只能使用可控测试微信号，不能使用真实客户或业务联系人
- 必须先关闭自动任务，只保留单人、单次、手动探针
- 第一次验证只能做到“打开弹窗后取消”，不能直接点确定
- 所有验证动作必须进入 `wechat_action_lock`
- 验证日志需要记录目标、步骤、控件定位结果和是否真实发送，方便回放问题

1. 探测控件，不发送
   - 准备一个可控测试号 A 和测试号 B，让 B 删除 A，A 侧会话出现 `发送朋友验证`
   - 用 `wx.ChatWith(target, exact=True)` 打开目标会话
   - 调用 `wx.GetAllMessage()` 或 UIA 控件树探测，确认页面里能读到“开启了朋友验证”和 `发送朋友验证`
   - 记录 `发送朋友验证` 的控件类型、Name、AutomationId、BoundingRectangle

2. 点击入口，只呼出弹窗
   - 自动点击 `发送朋友验证`
   - 验证是否出现标题为 `申请添加朋友` 的弹窗
   - 验证弹窗里能定位到附加消息输入框、备注输入框、标签入口、朋友权限选项、`确定` 和 `取消`
   - 本阶段必须点击 `取消` 关闭弹窗，不真正发送

3. 真实发送一次
   - 仍然只用测试号
   - 填入固定测试文案，例如 `WXBot自动化验证`
   - 选择权限和备注后点击 `确定`
   - 在 UI 或返回记录里确认本次申请已发出
   - B 侧确认能收到好友验证请求

验证通过标准：

- 能稳定打开目标会话，且不会误进同名联系人
- 能稳定找到当前可见会话里的 `发送朋友验证`
- 点击后能稳定出现 `申请添加朋友` 弹窗
- 能填写附加消息和备注，能选择权限
- 点击取消时不会发送申请
- 点击确定时测试号能收到申请
- 失败时能给出明确原因，例如“未找到发送朋友验证入口”“未出现申请弹窗”“找不到确定按钮”

验证不通过时的处理：

- 不把 `conversation_verify_sender` 放入自动任务
- UI 中对 `删除我的人` 来源显示“当前微信版本未验证，暂不可自动发送”
- 仍可保留候选刷新、文案配置和限流配置，等发送器验证通过后启用

验证通过后的实现要求：

- 先支持手动单次发送，再开放自动调度
- 自动调度必须默认关闭，用户手动开启
- 每次只处理一个候选，执行前再次确认会话中仍存在 `发送朋友验证`
- 如果目标会话已经恢复正常聊天，不再发送申请，并把候选标记为 `skipped/recovered`
- 如果出现同名会话、未找到入口、弹窗标题不匹配、按钮不可点击，全部按失败处理，不做坐标盲点

## 调度与限流

调度原则：

- 所有真实微信操作必须进入 `wechat_action_lock`
- 一次只发送一个好友申请
- 不和新好友自动通过、通讯录维护、关系扫描标签同步抢同一段微信 UI
- 保存配置后，运行中任务应热同步；已经开始的一次发送先完成

每日限额：

- 以账号级、自然日统计
- 统计“已发出申请”的次数，不统计候选扫描次数
- 如果 wxauto 返回明确失败且没有发出申请，可以计入失败，不计入今日已发送
- 如果无法判断是否发出，为保守起见计入今日已发送，避免重复打扰

间隔随机数：

- 用户填写基础间隔，例如 30 分钟
- 默认抖动：`max(1 分钟, 基础间隔 * 10%)`
- 30 分钟会落在 27-33 分钟之间
- 用户描述里的 29 或 32 分钟属于这个范围

时间段：

- 支持多个时间段，例如 `09:30-12:00`、`14:00-21:30`
- 当前时间不在时间段内时，不发送，计算下一次可发送时间
- 跨天时间段后续再做，例如 `22:00-01:00`，第一期可先不支持并在 UI 校验

## 去重与跳过

候选去重优先级：

1. `wechat_id`
2. `phone`
3. `remark + nickname`
4. `display_name`

跳过规则：

- 缺少可搜索关键词
- 命中排除标签
- 今天已达到上限
- 当前不在发送时间段
- 距离上次申请未达到间隔
- 该候选今天已经发送过
- 该候选最近 N 天已发送过，默认建议 7 天
- 微信操作锁占用中

失败记录：

- 保存 wxauto 返回的 `WxResponse` 状态和 message
- 保存异常摘要，不保存完整堆栈到用户可见 UI
- 连续失败达到阈值时自动暂停任务，例如连续 5 次失败

## 和现有能力的关系

与【新好友】自动通过：

- 新好友自动通过负责“别人加我”
- 好友申请负责“我去加别人”
- 两者共享页面，但运行逻辑独立

与【关系扫描】：

- 关系扫描负责识别并维护 `删除我的人` 标签
- 好友申请可以读取该标签作为一个来源
- 发送申请后不要立即移除 `删除我的人`；等对方通过或关系扫描恢复后再处理

与【通讯录维护】：

- 标签来源依赖本地通讯录档案
- 如果本地通讯录未建档，UI 应提示先做通讯录维护
- 标签选择器复用现有通讯录标签统计

与【关键词回复】：

- 左侧文案规则只借鉴交互样式，不复用关键词回复的触发逻辑
- 这里的“匹配”是匹配联系人标签，不是匹配聊天消息内容

## 风险与防护

微信风控风险：

- 批量添加好友天然容易触发风控
- 默认每日上限要保守，例如 20
- 默认间隔不低于 30 分钟更稳
- UI 需要提示“频繁添加可能触发微信限制”

误加风险：

- 标签来源必须展示候选预览和数量
- 保存前校验至少选择一个来源标签
- 支持排除标签，避免加到内部号、黑名单、已无需处理的人

重复打扰：

- 记录最近申请时间
- 默认 7 天内不重复申请同一人
- 无法确认是否发出时按“已发送”处理

资料不足：

- 候选缺少微信号/手机号时，只能尝试昵称/备注搜索，命中不确定
- UI 中把这类候选标记为“低置信”
- 第一期可默认跳过低置信候选，或者做一个“允许用昵称搜索”的高级开关
