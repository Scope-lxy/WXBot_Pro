# 微信 UI 并发实测结果

本文记录 2026-07-10 对 wxautox4 / 微信真实 UI 操作的并发测试。结论用于约束 WXBot Pro 的 UI 调度，不代表 wxautox4 官方能力承诺，也不把一次成功当作永久安全保证。

测试统一使用 UTF-8，测试好友为 `阿英2`、`阿英3`、`阿英4`、`炳3`、`炳4`。v2 测试读取 20 个联系人、15 条历史消息，语音素材长 3 秒；每个场景在独立子进程中运行，超时后按 PID 终止进程树，并在场景结束后执行一次子窗口读消息探活。

每个并发操作线程都单独执行 `pythoncom.CoInitialize()`，并在该线程内创建自己的 `WeChat()`、重新取得目标子窗口。测试结果证明这种线程/对象归属模型下可以并发，不证明同一个 `bot.wx`、Chat 或 Message 对象能够跨线程安全复用；生产实现必须采用相同模型或另做专项验证。

第一轮 v2 中语音 baseline 和“语音 + 文字”因为子进程未找到 ffmpeg 而失败，这两项不是微信 UI 冲突证据，已在第二轮修正环境后重测。其余原始失败和超时均保留，不用成功场景覆盖失败样本。

## v2 实测结果

### 单操作基线

| 操作 | 耗时 | 结果 |
| --- | ---: | --- |
| 子窗口读取 15 条可见消息 | `3.074s` | 成功 |
| 子窗口发送文字 | `1.255s` | 成功 |
| 主窗口读取 15 条历史消息 | `6.969s` | 成功 |
| 子窗口发送 3 秒语音 | `8.962s` | 成功；包含首次 ffmpeg / 发送链路开销 |
| 子窗口发送文件 | `1.288s` | 成功 |
| 通讯录读取 20 人 | 连续两轮超过 `75s` 未返回 | 失败；说明通讯录读取自身耗时波动很大 |

### 自动关系扫描计时

自动关系扫描只调用一次 `GetSession()` 读取当前会话列表，不滚动深列表。生产机器人正常停止后，计时探针通过同一套 `WeChatUIRuntime + WeChatUIOwner` 背靠背执行 10 次：

- 第 1 次冷态扫描 `0.172226s`。
- 后续 9 次为 `0.009871–0.015785s`。
- 10 次纯扫描合计 `0.286093s`，平均 `0.028609s`，中位数 `0.012190s`，P95 / 最大值 `0.172226s`。
- 每次都读取 `17` 个会话，没有异常、数量漂移、关系数据写入或残留探针进程。

生产形态另以原 10 秒周期连续观察 12 轮自动调度，实际完成间隔为 `10–12s`，平均 `11.455s`，运行实例保持不变。期间另一端按顺序发送 A / B / C 三条私聊，三条各落 history 一次并只产生一轮合并回复，自动扫描继续推进，没有 UI 超时、错误窗口或重复回复。这证明 10 秒周期对当前 17 会话样本没有稳定性负担；考虑关系变化不需要秒级发现，产品最终把周期固定为 `30s`，面板不暴露参数。该结论不代表手动全量滚动扫描也能按相同频率执行。

关系标签写回采用与自动扫描不同的重操作规则：每个联系人是一个独立 `CONTACT_EDIT`，一次调度只处理 1 人；面板“标签同步间隔”可设置为 1–100 秒，默认 30 秒，失败对象 10 分钟后重试。自动回归已覆盖单人边界、配置间隔边界以及成功状态落盘，避免连续多人阻塞聊天或成功后重复修改。单个真实标签编辑耗时及编辑期间入站消息的端到端延迟仍需可逆实机验证，不能从 `GetSession()` 的毫秒级耗时外推。

### 生产形态通讯录强制终止恢复

`probe_contact_worker_preemption.py` 直接启动现有 `feature/contact_auto_collector_worker.py`，比线程矩阵更接近生产形态：

- 50 人采集子进程运行时，两个已有子窗口同时读取成功，耗时 `9.557s / 10.530s`，采集子进程仍存活。
- 按 PID 终止采集进程树耗时 `0.338s`，没有生成结果文件，因此不存在半成品被合并的机会。
- 终止后 `SwitchToChat` 成功，重新建立 `炳4` 子窗口耗时 `0.055s`，随后文字发送和消息读取均成功。

该结果证明通讯录子进程达到自身硬超时或收到用户停止时，可以按 PID 强制终止，并在终止后恢复聊天 UI。它不能作为后来聊天任务打断正在运行 UI 操作的依据；正常调度必须等待当前批次结束。

本轮可复查结果已经呈现清晰边界：通讯录与子窗口轻读写可以重叠；通讯录与文件、语音或其他主窗口动作重叠时，可能出现通讯录不返回、控件查找失败或耗时成倍拉长。

## 能够确认的边界

微信 UI 不是单通道。已经建立的不同子窗口可以并行读取和发送文字，也可以在通讯录读取期间继续轻量读写。

微信 UI 也不是彼此隔离的任意多通道。主窗口焦点、控件树、文件 / 语音发送链路以及 wxautox4 内部状态存在共享资源。并发操作可能都成功，也可能让其中一个操作永久不返回，所以“消息已经发出去”不能证明另一侧仍健康。

`GetFriendDetails(timeout=...)` 不是可靠的进程级截止线。20 人 baseline 连续两次超过测试时限，但同样的读取在轻并发场景下又分别于 `30.082s` 和 `49.100s` 返回。通讯录维护必须继续由最小子进程承载，并由父进程按 PID 执行硬超时终止。

当前 wxautox4 40.1.15 的 callback 实机契约与 `.pyi` 注释不一致：callback 返回 `False` 会继续滚动寻找起点，第一次返回 `True` 会停止 callback，并从命中项开始读取 `n` 人；命中项既是 `result[0]`，也计入 `n`。callback 原始 detail 只有名称字符串，没有微信号，因此名称只能定位，不能证明身份，更不能用“同名第几次”作为分页依据。

本轮每个组合只测了少量样本，尚未覆盖回调到达瞬间、通讯录结束后 `AddListenChat` 排队接续、素材转发排队接续、群聊引用发送和长时间压力运行。因此文档只给出保守调度边界，不把未测组合写成“安全”。

探针没有证明缓存 wxautox 对象后交给其他线程使用是安全的。当前生产实现只跨线程传纯数据，由 UI owner 重新取得窗口和消息对象；后续压力测试仍需持续观察对象归属边界是否存在遗漏。

## 调度建议

审查后不采用覆盖通讯录的一把全局 UI 锁，也不采用彼此独立的“一个重操作 + 两个轻操作”三路模型。后者理论上仍会同时放出三次 wxautox 调用，而三路读取已经实测明显退化。

实测给出的是安全上限，不代表生产必须同时使用两路通用聊天操作：

1. 两路子窗口读取并发约 `6.9s` 才全部完成，按单路基线顺序执行两次约 `6.1s`，没有吞吐收益。
2. 两路文字并发最慢约 `2.2s`，按单路基线顺序执行两次约 `2.5s`，收益只有约 `0.3s`。
3. “通讯录 + 一路已有子窗口文字”能避免数分钟维护期阻断聊天，运营收益明确。

实测说明“通讯录 + 一路已有子窗口”在当前版本技术上可行，但生产最终主动不使用这项能力。只保留一个专用 UI owner 线程；通讯录子进程运行时，owner 和消息业务线程都停在统一屏障前，完成或 300 秒硬超时并恢复聊天页后再按 FIFO 继续。回复可能晚几分钟，但调度逻辑更小，错回复、history 污染和 UI 干扰风险更低。

`GetNextNewMessage`、`GetListenMessage`、图片下载和回调到达瞬间没有包含在本轮矩阵中，不能外推为安全。生产统一在通讯录屏障后排队；周期轮询只保留一个位于原 FIFO 位置的 poll-due，不能让通讯录永久无法启动，也不能在恢复后越过更早的业务任务。

已经开始的 UI 操作优先完成，后到任务不能抢占。通讯录运行时，文字、图片、语音、文件、转发、监听维护、主窗口和 UIA 动作全部等待，AI 业务处理也不提前开始。当前批次自然结束或达到自身 300 秒硬超时后，先恢复聊天页，再按原到达顺序处理；只有积压任务清空且到达下一维护间隔时，才允许启动下一批通讯录。

## 通讯录数据边界

并发改造不删减通讯录字段。自动维护固定每批读取 50 人，不再向用户暴露批次人数配置。

- 删除面板 `20 / 50 / 80` 三档选择和对应配置项，代码内固定每批 50 人。批次人数只控制单批处理多少联系人，不改变每个联系人的详情读取内容。
- 继续通过 `GetFriendDetails` 读取与当前实现相同的好友详情，再按现有 v2 真源结构保存 `contact_key`、`wechat_id`、`wxid`、`nickname`、`remark`、`region`、`source`、`added_at`、`signature`、`tags`、`status`、`warnings` 及现有身份 / 关系状态字段。
- `display_name`、`send_name`、`send_target` 仍是运行时派生值，不写回联系人真源；这属于现有数据边界，不是本次稳定性方案删字段。
- 单批成功后增量合并；失败、超时或用户停止时不覆盖正式通讯录。只有完整一轮明确扫到尾部后，才允许处理“本轮未出现联系人”的失效状态，不能根据一个短批次删除联系人。
- 固定 50 的代价是失去 20 人短批次选择，但实测中 20 人读取也会不返回，说明批次档位不是可靠的稳定性开关。风险统一由父进程硬超时处理，避免把底层异常转嫁给用户调参。
- 每批进入通讯录后先用 Home 回顶并验证“新的朋友”固定入口；从顶部以精确名称定位后，再用微信号 / wxid 或完整资料指纹核验身份。没有安全游标、首项身份不一致或回顶失败时拒绝合并，不在未知位置继续采集。
- wxautox4 在通讯录末尾可能返回同一身份的多条虚拟重复行；生产 worker 按稳定身份去重。正常批次短批后只运行 `n=2` 尾部探针；至少两条原始结果都属于锚点身份且没有新身份时才结束完整轮，单行、异常或超时均保留游标。

## 最终生产形态复测

- 回顶修复后，通讯录 50 人连续三批自然完成，耗时 `42.114 / 44.538 / 49.234s`；加入稳定身份协议后再次连续三批完成，耗时 `43.757 / 46.956 / 51.970s`，第二、三批首项名称和微信号都与请求锚点一致。最终删除无效的同名 occurrence 状态后，两批复测为 `41.350 / 44.367s`。
- 每批均完整返回昵称、备注、微信号、地区、来源、标签、添加时间、个性签名 8 个资料字段。
- 真实尾部名称为全角 `！！！`；wxautox4 原始返回 5 行相同微信号，按稳定身份去重后为 1 人。生产 `n=2` 尾部探针又在 `98.417s` 后返回原始 2 行相同微信号、去重后 1 人，正式 `contacts.json` 未改变；报告位于 `backups/contact_tail_probe/20260711_130529/result.json`。这证明当前微信内核的尾部虚拟重复能为小探针提供稳定身份凭据。
- 历史探针曾证明通讯录期间已有子窗口轻量快照和文字发送可行；这些结果只证明底层能力，不再代表生产调度策略。最终生产策略更保守：通讯录屏障期间全部等待。
- 手动关系全量扫描修复前耗时 `277.28s`，读取 `1201` 个会话，滚动 `262` 次后自然完成；耗时主要来自每次滚动固定等待 1 秒。该等待原本服务于已经删除的滚动分片方案，在当前连续 owner 事务中没有作用。
- 删除逐次等待后，同一账号在 `14s` 内读取 `1202` 个会话，仍为 `262` 次滚动，状态正确保持 `completed`，未命中 1000 次保险上限。自动短扫描在 owner 返回后重新加载最新状态，避免用排队前的旧 `running` 覆盖全量结果。
- 因此手动关系全量扫描最终采用一个连续 owner 独占事务，不做滚动分片，不在中间插入回复，也不提供停止按钮。

本轮全扫识别 `187` 个删除关系、`94` 个拉黑关系。标签同步实机对拉黑、删除状态均取得成功样本；单个失败对象保留待同步并进入 10 分钟重试，没有误报成功。

后续 5 人标签压力实测暴露了重绑副作用：`细妹小号` 在微信中连续发送“干扰测试1 / 干扰操作2”，第一条于标签任务间隙进入日志和 history，第二条落在单个标签失败触发的整客户端重绑期间，微信可见但日志与 history 均缺失。生产因此取消普通标签失败的立即重绑，并把通用重绑条件收紧为明确的 Windows 无效窗口句柄或 COM/RPC 客户端断开；控件超时、目标不匹配和业务失败只结束当前任务。

收紧重绑后的组合回归中，`细妹小号` 在 3 个标签任务期间发送“回归测试A / 回归测试B”，两条消息均进入日志和 history，各出现 1 次并按顺序合并为一轮回复；微信端确认实际收到回复，全程未重绑。首次 3 个标签任务都失败后对照 Git 旧版发现，owner 迁移漏掉了主窗口置前和移开鼠标两个焦点稳定步骤；把旧版完整 `ChatWith -> ChatInfo -> EditFriendInfo` 动作序列适配回 owner 后，`B-苏纯叶 / 阿姣 / 彩凤` 三人实测全部同步成功，分别覆盖删除和拉黑标签，无重绑且机器人持续在线。

## 旧版多步骤任务对照

owner 迁移完成后又按 Git `HEAD` 逐项核对了多步骤任务，避免为了统一调度删掉旧版经过实机验证的必要步骤：

| 任务 | 当前保留的完整步骤 | 迁移审查结果 |
| --- | --- | --- |
| 备注 / 标签 | 主窗口置前 -> `ChatWith` -> 再置前并移开鼠标 -> `ChatInfo` 核对目标与现有标签 -> `EditFriendInfo` -> 清理旧名称子窗口 | 已补回迁移时漏掉的焦点步骤；普通失败不重绑 |
| 素材池重建 | 子窗口内部历史 -> 子窗口公开历史 -> 主窗口历史 -> 子窗口可见消息；无可转发结果时保留旧素材池 | 已恢复旧版降级顺序，每个读取器失败后继续下一方案 |
| 素材 / AI 自动转发 | 按稳定签名重定位素材 -> 滚动到可操作区域 -> 原生 `forward` -> 明确结果落盘；句柄失效时只定向刷新后重试 | 两类转发共用同一 owner 底座；结果未知冻结，不盲目重发 |
| 定时消息 | 目标解析 -> 每项写 `inflight` -> 单项发送 -> 单项结果落盘 -> 下一项前检查停止和任务版本 | 删除生产批量分支，未开始项可取消 |
| 新好友 | 每轮重新读取并唯一定位 -> 只接受 1 人 -> 切回聊天页 -> 逐项发送欢迎文字 / 文件 | 避免联系人页变化后继续使用旧 `NewFriend` 对象 |
| 主动好友申请 | 最多两次重新定位和提交前校验 -> 真正提交一次 -> 明确结果落盘 | 继续复用旧 `ConversationVerifySender`；提交结果未知标记 `uncertain` |
| 朋友圈 | 打开后等待 `2~5s` -> `Publish` -> 等待 `9~12s` -> 校验编辑器关闭和最新内容 -> 等待 `2~5s` 后关闭 | owner 内保留旧版稳定等待；自动测试不真实发布 |
| 私聊 / 群聊多气泡 | 第一条不额外延迟；后续气泡按私聊 / 群聊独立开关决定是否使用固定标准间隔；每条分别提交 | quote 后续文字、关键词、新好友欢迎和定时内容均不得合成不可取消整组 |

相关组合专项回归共 `127` 项通过，覆盖通讯录 / 备注、素材池 / 转发、朋友圈、定时消息、好友申请、进程中断和运行状态落盘。真实朋友圈发布属于不可逆操作，本轮只验证 owner 顺序、稳定等待和模拟发布。

## 对抗式审查

### 已发现并修正的问题

| 原方案风险 | 对抗场景 | 修正 |
| --- | --- | --- |
| 主窗口锁、重发送锁需要嵌套 | 两个线程以不同顺序取锁会死锁，规则也难长期维护 | 一个进程内 UI owner 串行真实调用，删除发送锁和嵌套 |
| 继续保留批次人数三档 | 多一个低价值控制项、校验分支和测试矩阵，用户还可能误以为人数会影响字段完整性 | 删除三档和对应配置，自动维护固定每批 50 人 |
| 仅依赖内核 timeout | 内核调用永久不返回时，Python 线程无法被安全杀死 | 通讯录保留最小子进程和父进程硬超时 |
| 后到聊天任务打断通讯录 | 当前 UI 状态被强行切换，可能留下游标、页面和数据状态不一致 | 已开始的通讯录优先完成；聊天重操作排队，并优先于下一批后台任务 |
| 所有子窗口无限并发 | 两路读取已没有总吞吐收益，更多并发继续放大抖动 | 不启用第二个通用聊天 worker，通讯录期间 owner 不操作微信 |
| 把并发上限当成必须利用的能力 | 为约 `0~0.3s` 收益引入容量、generation 和跨 worker 对象管理 | 并发只用于能避免数分钟阻塞的通讯录场景 |
| 未测试 GetNext 就按轻操作放行 | 可能切换主窗口并干扰联系人扫描 | 先按独占，通讯录结束后合并补轮询 |
| 复用一次消息快照过久 | 语音首次只有时长时，旧快照永远读不到稍后出现的正文 | 首次发现后约 `5s / 10s` 分别重新 `GetAllMessage()`，仍无正文才静默忽略 |
| 把任意线程超时当成可恢复 | Python 无法安全终止卡死线程，继续运行会留下半死状态 | 通讯录只杀子进程；其他 wxautox 调用超时则记录栈并重启机器人进程 |

### 残余风险

1. **长时间并发稳定性**：短矩阵和连续批次已经通过，但仍不能替代数小时真实高峰运行观察；上线后继续关注漏回复、错误窗口和孤儿子进程指标。
2. **单次发送的视觉落盘确认**：owner 实机发送返回微信明确成功，但一次测试快照没有看到刚发送文本。为避免重复打扰没有盲目重发，仍需在日常运营中观察 self 回声证据。
3. **底层版本变化**：结论基于当前 wxautox4 和微信版本。升级后需重新跑通讯录、关系全扫和卡死恢复；生产仍默认不开放通讯录期间聊天穿插。
4. **停止时的依赖内部晚到异常**：短生命周期 owner 探针在 `StopListening()` 返回并完成 shutdown 后，wxautox 内部监听线程曾晚到一次 `ListControl` 查找超时。它没有影响已完成的发送或 owner 停止，业务层也没有跨线程保存 Chat / Message；仍需在长时间正式运行的停止场景观察是否只是依赖退出噪声。

## 最终判断

生产实现已经收敛为“一个专用 UI owner 线程 + 一个通讯录专用子进程 + 一条纯数据意图队列 + 一个通讯录全屏障”。底层并发能力保留为实测事实，但生产不再用回复速度交换额外调度复杂度。

手动关系全量扫描采用连续独占是有意的产品选择：它是用户主动发起、通常几十秒到几分钟完成的完整性任务。扫描期间聊天 UI 排队，换取从顶部到末尾的一次性完整结果；这与后台通讯录自动维护的分批调度不是同一种任务。
