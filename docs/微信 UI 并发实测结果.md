# 微信 UI 并发实测结果

本文记录 2026-07-10 对 wxautox4 / 微信真实 UI 操作的并发测试结果。结论用于复查机器人 UI 锁策略，不作为 wxautox4 官方能力承诺。

覆盖的 UI 原语：

- 子窗口动作：`GetAllMessage`、`SendMsg`、`SendFiles`、`SendAudio`
- 素材转发：`message.forward`

## 关键测试结果

| 场景 | 结果 | 结论 |
| --- | --- | --- |
| 通讯录 50 人读取 baseline | `46.8s`，成功 | 50 人短批次本身可接受 |
| 素材池主窗口历史读取 baseline | `10.9s`，成功 | 读取历史是中等耗时主窗口动作 |
| 子窗口 12 秒语音 baseline | `12.6s`，成功 | 语音发送会占用约等于语音时长的 UI 时间 |
| 主窗口 12 秒语音 baseline | `13.6s`，成功 | 主窗口语音同样是重 UI 动作 |
| 通讯录读取 + 子窗口文字 / 读消息 | 通讯录 `48.8s`，子窗口文字 `0.8s`，读消息 `4.1s`，均成功 | 轻量子窗口文字和读取可与通讯录短批次并行 |
| 通讯录读取 + 子窗口文件 / 12 秒语音 / 素材转发 | 子窗口动作成功，但通讯录线程 120 秒未结束 | 高风险：子窗口重动作会反向拖住通讯录读取 |
| 通讯录读取 + 素材池主窗口历史读取 | 历史读取失败：`Find Control Timeout: {ControlType: EditControl}` | 明确冲突：两个主窗口动作不能并行 |
| 通讯录读取 + 主窗口文字 / 文件 / 语音 | 全部成功，但文字 `32.3s`、文件 `62.6s`、语音 `92.3s`，通讯录 `69.0s` | 主窗口发送与通讯录会互相拖慢 |
| 素材池主窗口历史读取 + 子窗口文字 / 语音 / 文件 | 全部成功，但子窗口发送被拖到 `11s ~ 23s` | 可并发但体验差，应视为排队竞争 |
| 素材池主窗口历史读取 + 素材转发 / 主窗口发送 | 全部成功，素材转发 `30.2s` | 多个重动作叠加会显著拉长耗时 |
| 主窗口 `ChatWith` / `ChatInfo` + 子窗口文字 / 读消息 | 全部成功，耗时小 | 短主窗口动作与轻量子窗口动作风险较低 |
| 主窗口文字 / 文件 + 子窗口读消息或文字 | 全部成功，耗时小到中等 | 单次轻发送组合可接受 |
| 主窗口 12 秒语音 + 子窗口文字 | 主语音 `13.4s`，子窗口文字 `14.3s` | 语音会拖住其他发送 |
| 子窗口文字 / 文件 / 12 秒语音并发 | 全部成功，但文字和文件被语音拖到 `13s ~ 14s` | 子窗口之间不是完全独立，语音应串行 |
| 子窗口素材转发 / 文字 / 文件 / 12 秒语音 / 读消息并发 | 全部成功，但读消息 `20.7s`、转发 `21.9s` | 多个子窗口重动作会互相排队或拖慢 |

## 实测结论

微信 UI 不是绝对单车道。已有子窗口的轻量文字发送和可见消息读取，可以在部分主窗口动作进行时成功执行。

但微信 UI 也不是可以随意并行的多车道。`GetFriendDetails`、`ChatWith + GetHistoryMessage`、`SendAudio`、`SendFiles`、`message.forward` 这些动作会争用微信 UI、焦点、控件搜索、文件/语音发送链路或 wxautox4 内部锁。它们并发时即使都能成功，也会出现耗时成倍拉长、控件查找失败、通讯录读取不返回等问题。

最重要的风险是：不能只看“子窗口消息发出去了”。实测里子窗口文件、语音和素材转发都能在通讯录读取期间成功，但通讯录读取线程没有正常结束。这会直接影响自动维护稳定性。
