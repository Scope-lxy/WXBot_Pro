# 全局监听最小修复方案

本文记录针对“活跃好友持续得到回复、其他未监听好友长期得不到处理”问题形成的第一阶段最小修复方案。结论依据 2026-07-15 运行日志、当前 WXBot Pro 代码和 2026-07-16 wxautox4 实机测试。

第一阶段已于 2026-07-16 落地；本文同时保留实测依据、实现边界和验收标准。第二阶段 `deep` 深度恢复已有具体方案和上线门槛，但仍未实施。

第一阶段只解决公平扫描、先保存后建窗、正常可见尾部补洞和截断降级提示。已确认截断后的深度历史恢复单独作为第二阶段，不在第一阶段自动执行。

## 一、问题与目标

当前全局监听每轮只调用一次 `GetNextNewMessage`。消息返回后，同一调用链还会同步建子窗口、处理其他微信 UI 任务，并在主循环末尾等待。结果是已经拥有子窗口的活跃好友可以持续进入 callback 和回复流水线，尚未被全局扫描发现的好友则可能等待很久。

修复目标：

1. 已监听会话和未监听会话都不能无限饿死。
2. 必须先保存微信未读消息，再建立长期监听子窗口。
3. 扫描、建窗、补洞、AI 和发送之间职责清楚，不增加重复消息真源。
4. 微信 UI 继续由唯一 owner 非抢占执行，业务和 AI 可以并行。
5. 保持开发者原始 wxautox4 参数，不通过延长单次扫描掩盖调度问题。

## 二、实测确认的 wxautox4 行为

### 2.1 `GetNextNewMessage` 使用微信主窗口

对“细妹小号”准备 25 条未读消息后，单独调用一次 `GetNextNewMessage`：

- 微信主窗口切换到对应好友聊天页并向上滚动。
- 没有弹出独立监听子窗口。
- 调用前后 `GetAllSubWindow` 均不存在该好友子窗口。
- 总耗时 `11.229s`。

因此，用户看到的积压消息滚动发生在微信主窗口，不是长期监听子窗口。

### 2.2 `AddListenChat` 不回放建窗前积压

在“细妹小号”有 25 条未读且没有子窗口时，直接执行 `AddListenChat`：

- 建窗耗时 `0.401s`。
- 建窗后观察 `12s`，callback 收到 `0` 条。
- wxautox 日志只有切换会话、打开独立窗口和缓存窗口，没有向上滚动记录。
- 微信会话未读数从 25 变成 0。

因此，`AddListenChat` 只建立未来消息监听。它会让会话变成已读，但不会把建窗前积压交给 callback。

### 2.3 `GetAllMessage` 只覆盖当前可见尾部

上述 25 条消息由 20 条文字、4 张图片和1条语音组成。直接建窗后执行 `GetAllMessage`，只读取到当前屏幕可见的最后4条：3张图片和1条语音。

因此，普通 `GetAllMessage` 适合修复短暂交接期的可见尾部缺口，不能替代全局未读扫描，也不能承担已确认截断后的深度恢复。

### 2.4 `GetNextNewMessage` 存在数量和时间双上限

当前 wxautox4 40.1.15 原始参数为：

```text
GET_NEXT_MAX_QUANTITY = 30
GET_NEXT_MAX_RUNTIME = 10
```

项目不覆盖这两个参数。

25 条未读实测中，`GetNextNewMessage` 在主窗口滚动到“新消息3”时达到10秒内部运行上限并强制停止：

- 调用前微信显示25条未读。
- 接口只返回23条。
- 返回结果包括4张图片、语音时长占位和“新消息3”至“新消息20”。
- 最早的“新消息1、2”没有返回。
- 会话仍然被微信标记为已读。

这证明返回数量小于30也可能被时间上限截断。不能使用“返回不足30条”推断扫描完整。

### 2.5 普通快照不能找回时间截断的旧消息

上述扫描结束后，立即读取微信主窗口普通快照，只看到了“新消息15”至“新消息20”和附近图片，没有找回“新消息1、2”。

因此，已确认时间截断时需要带滚动能力的有界深度补洞；再次调用 `GetAllMessage` 不足以恢复。

## 三、第一性原理结论

正确顺序必须固定为：

```text
GetNextNewMessage 先发现并保存已有未读
-> 按需 AddListenChat 接管未来消息
-> 对扫描与 callback 之间的交接空隙补洞
-> AI 处理
-> UI owner 发送
```

禁止改成：

```text
先 AddListenChat
-> 再依靠 callback 或 GetAllMessage 找积压
```

实测证明后一种顺序可能同时发生：未读标记被清除、callback 收不到积压、普通快照只能看到最后几条。

## 四、最小运行结构

最终只保留以下五个既有责任边界：

```text
一个全局扫描泵
+ 一个微信 UI owner FIFO
+ 一个 ListenerWindowSupervisor
+ 一个按会话带代次的 tail 补洞状态
+ 现有 SQLite 消息事实库和回复流水线
```

不新增双优先级调度器、每会话建窗线程、第二套消息队列或独立补洞队列。

## 五、全局扫描泵

### 5.0 两阶段启动

启动时先创建微信 client 并取得账号身份，但不立即为固定或动态会话调用 `AddListenChat`。账号级 SQLite 和消息运行时准备完成后先启动全局扫描；已有未读安全落库后，再由现有 supervisor 补齐固定和动态监听窗口。监听器运行期重建也回到同一顺序：`StopListening` 先使当前 runtime 的窗口登记失效，`StartListening` 后重新扫描到空，再放行 supervisor 补窗。这样启动和恢复都不会在消息库准备或补扫完成前吞掉未读。

### 5.1 调度规则

启动后立即启动一个独立扫描泵：

1. 任意时刻最多保留一个待执行 `POLL_MESSAGES`。
2. 扫描任务进入现有 UI owner FIFO。
3. 返回非空时，尽快把下一次扫描排到 FIFO 尾部。
4. 返回空时，恢复普通低频轮询。
5. 不固定“扫描一次、回复一次”，也不增加期限优先级队列。

由于 FIFO 中最多只有一个扫描任务，扫描不会淹没回复；扫描一旦排队，后来的任务也不能无限越过它。

### 5.2 扫描前未读快照

在同一个 owner 动作内，调用 `GetNextNewMessage` 前先读取一次轻量会话列表，记录可见未读会话的：

- 会话名；
- 会话类型；
- 未读数量；
- 是否免打扰。

`GetNextNewMessage` 返回会话名后，再从调用前快照取得该会话的预期未读数。快照没有目标或微信在两次读取间收到新消息时，只能作为辅助证据，不能宣称严格原子。

### 5.3 扫描结果持久化

扫描返回后：

1. 在 UI owner 边界把 wxautox Message 转换为纯数据。
2. 同一批消息一次性提交账号级 `message_store.sqlite3`。
3. SQLite 提交成功后，消息才进入现有业务队列。
4. 建窗成功与否不影响已经发现的消息。
5. SQLite 提交失败时停止继续扫描并显示覆盖降级。

微信标已读和 SQLite 提交无法形成真正的跨系统原子事务，因此不宣称 exactly-once。批量事务只能避免本地写入一半。

## 六、扫描完整性判断与降级

以下任一条件成立时，把该会话标记为“深度覆盖不完整”：

1. 返回的真实好友消息数小于调用前记录的未读数。
2. `GetNextNewMessage` 总耗时达到或超过 wxautox 的运行上限。
3. 返回数量达到 wxautox 的单次数量上限。
4. 扫描过程中发生异常，但微信会话已经被打开或标记为已读。

第一阶段不自动滚动深历史。已经取得的消息正常落库和回复，覆盖状态保持降级并记录预期未读数、实际返回数、扫描耗时和触发原因。未命中上述条件时，窗口恢复后执行普通 `tail` 补洞。

未读数比较必须按真实入站消息计算，不把时间分隔符、机器人 self 回声或其他系统行误算为好友未读消息。仅有时长的语音可能暂时表现为文本占位，不能按类型名称判断是否遗漏。

## 七、按需建窗

扫描消息安全落库后，只向现有 `ListenerWindowSupervisor` 登记建窗需求，不在扫描调用链同步等待建窗。

窗口管理规则：

1. 同一 `(chat_type, conversation)` 只保留一个建窗或恢复任务。
2. 所有建窗仍由 UI owner 执行。
3. `_add_chat` 必须先检查当前运行期已有窗口，再决定是否调用 `AddListenChat`。
4. `AddListenChat` 只负责未来消息，不承担积压恢复。
5. 建窗失败沿用现有 `30s / 60s / 60s` 重试和 `600s` 后每 `300s` 降级恢复。
6. 补洞不得在窗口不存在时隐式调用 `AddListenChat`。
7. 普通业务失败不得重绑整个微信客户端。

禁止在启动时预先给所有未读好友建立子窗口。必须先通过全局扫描保存未读事实，再按需建窗。

## 八、统一补洞状态

窗口和 tail 补洞状态继续按会话保存，不持有消息对象：

```text
generation
retry_at
inflight_generation
```

窗口从“不可信或不存在”变为“当前运行期可信可用”时：

```text
generation += 1
```

重复验证同一个可用窗口不重复生成补洞。

补洞领取当前 `generation`。成功时直接删除自己领取的标记；如果执行期间窗口再次失效并恢复，产生了更新代次，旧补洞成功不能误清新标记。没有窗口可用信号时不创建标记，也不执行补洞。

窗口“可信可用”至少要求：

- 会话名和内部 `chat_type` 匹配；
- 窗口属于当前 UI runtime；
- 当前运行期 callback 已注册；
- 没有已知的监听器失效证据。

## 九、第一阶段正常尾部补洞 `tail`

`tail` 不只覆盖扫描返回到 callback 稳定生效之间的几秒，而是覆盖会话在任何“监听不可信期间”产生、且仍位于当前可见尾部的历史缺口，包括：

- 机器人停止后重新启动；
- 子窗口被清理后重新建立；
- 子窗口丢失、监听器异常或微信客户端恢复；
- 全局扫描完成到当前运行期 callback 稳定接管之间；
- 当前 SQLite 尾部与微信可见窗口之间存在可信可修复缺口。

执行方式：

```text
GetAllMessage
-> 与 SQLite 尾部寻找可信重合边界
-> 找到当前消息边界
-> 只补入重合点到当前消息之前的可见尾部缺口
```

### 9.1 补洞成功条件

以下全部完成才算补洞成功：

1. 目标窗口身份校验通过。
2. 可见尾部快照读取成功。
3. 找到可信历史锚点，或能确认本轮需要覆盖的完整范围。
4. 缺失消息提交 SQLite 成功。

补入0条也可以成功，但必须确认确实没有可见尾部缺口。边界找不到、COM异常或 SQLite 失败时保留原补洞代次，并按退避时间重试。

### 9.2 第二阶段 `deep` 具体方案（未实施）

#### 9.2.1 已排除的错误方案

2026-07-16 对“细妹小号”的 35 条受控未读实测中：

- `GetNextNewMessage` 耗时 `11.469s`，只返回 `DEEP-09` 至 `DEEP-35` 共 27 条，微信随后清空未读标记。
- 连续四次 `GetHistoryMessage(30)` 都只返回 `DEEP-06` 至 `DEEP-35`，无法继续向前取得 `DEEP-01` 至 `DEEP-05`。
- 历史消息 `message_id` 跨读取不稳定。旧探针按 `message_id` 对四次历史快照和全局扫描求并集，最终错误形成 119 条受控记录，其中 89 条为重复出现。
- 另一次单次读取 50 条可以覆盖全部 35 条；同一批受控消息在两次 50 条读取中的 `hash / hash_text` 稳定。

因此第二阶段明确禁止：

- 反复读取固定 30 条并期待窗口自动向前翻页；
- 按跨读取 `message_id` 求并集；
- 按正文或 hash 集合去重；
- 找不到唯一边界时把整页历史全部写入；
- 为 deep 找回的每条旧消息单独补发回复。

#### 9.2.2 第一版支持范围

第一版只自动处理同时满足以下条件的会话：

1. 私聊；群聊的发送者、@文本和成员同名边界另做实测后再开放。
2. 扫描前未读数可信，范围为 `1–50`。
3. 全局扫描取得的真实好友消息数小于扫描前未读数，能够算出明确的 `missing_friend_count`。
4. 单次 `GetHistoryMessage(50)` 可以取得足够历史，并能和已经落库的扫描批次形成唯一的连续重合。
5. 重合所需消息都有经过实机验证可跨 `GetNextNewMessage / GetHistoryMessage` 保持一致的非空 `(hash, hash_text)`。

未读数缺失、超过 50、群聊、哈希缺失、特殊消息尚未验证或边界不唯一时，不猜测、不自动扩大读取量，继续显示覆盖降级。命中 30 条 / 10 秒边界但 `actual_friend_count >= expected_unread_count` 时，可证明扫描前已有未读均已取得，不创建 deep 缺口。

#### 9.2.3 运行顺序

仍只使用现有全局扫描泵和唯一 UI owner，不增加 deep 线程或第二套消息队列：

```text
GetNextNewMessage
-> 扫描批次与 deep 缺口证据在同一 SQLite 事务落盘
-> 正常会话立即进入现有业务队列
-> 有 deep 缺口的会话暂缓派发，也暂不 AddListenChat
-> 全局扫描继续，直到取得一次空结果
-> 同一扫描泵领取一个 deep 缺口并提交一个 owner 历史读取意图
-> deep 事务成功或明确阻断后，才派发已落库扫描消息并登记建窗
-> 两个 deep 缺口之间至少再执行一次全局扫描
```

这样大量普通未读仍先获得扫描机会；deep 只延后对应会话，不阻塞其他已安全落库会话的 AI。每次最多处理一个 deep，会话消息仍只存在于 `chat_events`，不创建待答 JSON 或内存消息副本。

#### 9.2.4 持久化状态

账号级 `message_store.sqlite3` 增加一份“扫描覆盖缺口状态”，每个降级扫描批次一行，只保存证据和状态，不保存第二份消息：

```text
gap_id
conversation / chat_type
scan_source_batch / scan_event_ids
expected_unread_count / actual_friend_count / missing_friend_count
status = pending | reading | resolved | blocked
reason / attempt_count / created_at / updated_at
```

`gap_id` 由账号、会话、扫描批次和未读证据生成。扫描事件与缺口行必须同事务提交，避免进程恰好在“消息已保存、缺口尚未登记”之间退出。启动恢复只放行没有活动缺口的 pending 入站；有缺口的会话仍由扫描泵先完成或阻断 deep，再进入现有回复恢复路径。

领取 deep 时先在事务内把 `pending` 改为 `reading` 并把 `attempt_count` 加一。第一版只允许一次自动读取，因此进程重启看到遗留 `reading` 时直接收敛为 `blocked` 并放行已保存消息，不再次读取；如果 deep 事件与 `resolved` 已在同一事务提交，则按成功结果恢复派发。

这张表是覆盖证据状态，不是消息真源，也不承担 AI 回复排队。它由现有扫描泵逐行领取，不创建独立 worker；deep 找回的消息仍只写 `chat_events`。普通可见 tail 的 `generation` 状态保持原职责，不与 deep gap 合并成一套泛化补洞框架。

#### 9.2.5 历史读取边界

deep owner 意图执行以下固定动作：

1. 确认没有为目标抢先建立子窗口。
2. `ChatWith(exact=True)` 精确切换目标，并用 `ChatInfo` 同时复核会话名和私聊类型。
3. 只调用一次 `GetHistoryMessage(50, interval=0.2, speed=5, goback=True)`。
4. 在 owner 内把结果复制成纯数据快照，原始 `Message` 不跨线程。
5. 读取后再次复核主窗口目标；目标变化、控件异常或超时均把本缺口标记为 `blocked`。

该动作是主窗口独占动作，通讯录屏障期间不执行；使用现有 owner watchdog 和 heartbeat，不创建专用 wxautox 客户端，也不并行读多个会话。

#### 9.2.6 唯一对齐与连续重复消息

正式合并不比较跨读取 `message_id`。对齐规则固定为：

1. 从 SQLite 读取原扫描批次的有序气泡及 `(hash, hash_text)`。
2. 在 50 条 deep 快照中查找扫描序列的连续位置；必须只有一个位置，且顺序完全一致。
3. 初版要求用于重合的扫描气泡全部具有经过实测确认的非空哈希对；不启用正文兜底。
4. 从重合起点向前倒推，直到恰好取得 `missing_friend_count` 条好友消息；其间的人工 `self` 可以作为上下文一起保留，系统行只提供时间信息，不写成消息事实。
5. deep 快照不足、好友条数不符、出现第二个可行对齐位置或任一哈希冲突时，整批 `blocked`，一条也不写。

重复的“好”“收到”、连续图片或相同时长语音不能按内容集合合并。它们按 deep 快照的窗口顺序逐个保留；相同哈希只有在前后序列能给出唯一对齐时才允许通过。整段都是不可区分的相同气泡时必须阻断，不能猜测少了第几条。

#### 9.2.7 SQLite 写入与幂等

新增一个明确的 `reconcile_deep_gap()` 事务入口，不复用普通 tail 的“无锚点就补整段”策略：

1. 重新校验 gap 仍为当前 `pending / reading` 代次，扫描锚点事件属于同一会话。
2. 在事务内完成唯一对齐、缺失数量核对、删除边界检查和事件插入。
3. deep 事件使用 `gap_id + deep_order` 作为稳定身份；历史读取到的原生 `message_id` 只放诊断 metadata，不参与事件 ID。
4. 写入 `source='wechat_deep_repair'`、`processing_state='handled'`、无回复 TTL、不推进会话版本、不创建回复任务。
5. 按顺序把缺失事件放在原扫描批次之前；同一 `gap_id` 重试第二次新增必须为 0。
6. 所有事件成功提交后，才把 gap 标记为 `resolved` 并清除该批覆盖降级。

如果 SQLite 事务失败则整体回滚。任何时候都不能出现“deep 写入一半，但覆盖状态显示已恢复”。

#### 9.2.8 回复、建窗和失败策略

- deep 成功：先提交缺失 history，再把原扫描消息送入现有会话合并与 AI 流水线，因此当前回复可以看到找回的上文；随后才向 supervisor 登记建窗。
- deep 证据不足或 UI 失败：标记 `blocked`，保留覆盖降级，但立即放行已经安全落库的扫描消息和后续建窗，不能让好友无限等待回复。
- deep 找回的旧消息只作 history，不单独触发 AI，不推进版本，也不取消已经存在的正常回复。
- 第一版每个 gap 只自动读取一次。失败后不自动扩大到 100 条、不循环滚动、不换另一套读取 API；重新尝试必须由后续明确方案或人工操作触发。
- 进程在 deep 前、中、提交后退出时，均以 SQLite gap 状态和 `chat_events` 为准恢复；不能依赖内存中的快照或 `_dispatched` 标记猜测。
- 首页在 `pending / reading` 时显示“深度恢复中”；`blocked` 显示原覆盖降级及具体阻断原因；只有同一会话全部 gap 都 `resolved` 才恢复正常状态。

#### 9.2.9 上线前必须通过的实测

第二阶段只有以下测试全部通过才能从“记录降级”切换为自动 deep：

1. 同一批 35 条受控消息同时记录全局扫描和 50 条历史快照，逐条证明 `(hash, hash_text)` 跨两个入口一致，而不只是两次历史读取互相一致。
2. 连续发送多条完全相同文字、相同图片、相同时长语音，并混入人工 `self`；最终 SQLite 气泡次数和顺序必须与微信一致。
3. 35 条场景最终恰好得到 35 条受控事实，不能是 34、36 或旧探针的 119；同一 gap 重跑新增 0。
4. 覆盖文字、图片、语音、引用、合并转发和时间分隔符；初版未通过的类型必须触发 `blocked`，不能降级为正文猜测。
5. 分别在扫描事务后、deep 读取中、deep 提交前、提交后派发前和建窗前强退；重启后不得漏回复、重复回复或重复 history。
6. 100 个普通未读会话混入多个 deep 会话时，普通扫描不能饿死；任意时刻仍只有一个 owner UI 动作和一个 deep 读取。
7. 目标窗口被人工切换、历史不足 50、未读超过 50、哈希缺失和 SQLite 冲突时都保持降级并安全放行已保存消息。

在第 1、2 项通过前，现有 `tools/probe_deep_unread_recovery.py` 只能作为反例和测试脚手架，不能直接搬入生产；它当前按不稳定 `message_id` 求并集的逻辑必须删除或重写。

## 十、回复流水线

不重写现有私聊合并、多气泡取消、会话版本和投递边界：

```text
SQLite 消息事实
-> 现有每会话消息合并
-> 同会话首次 AI 前尝试一次必要补洞
-> AI 生成可跨会话并行
-> 每个气泡独立进入 UI owner FIFO
-> 新消息通过会话版本取消尚未开始的旧气泡
```

tail 补洞找回的消息进入同一轮会话上下文，不为每条旧消息创建独立补发回复。补洞第一次失败时不能无限阻塞会话；使用已经安全落库的消息继续当前回复，同时保留补洞标记等待下次退避重试。已经开始的微信发送继续遵守结果未知即 `uncertain`、禁止自动重发的规则。

## 十一、通讯录、恢复和清理

通讯录自动维护只有同时满足以下条件才允许开始：

- 最近一次符合过滤规则的全局扫描为空；
- 没有待处理回复；
- 没有随当前入站 / 回复正在执行的 tail 补洞或窗口恢复；仅等待下一条消息触发的 dormant 代次不单独阻塞维护；
- 扫描器没有处于覆盖降级；
- UI owner 空闲；
- 持续安静一段时间。

当前直接返回 `True` 的自动维护空闲判断必须修正。

窗口恢复和动态窗口清理属于低优先级维护：

- 每次最多处理一个会话；
- 保护固定监听、待回复和正在恢复的会话；
- 不在扫描调用链同步批量清理；
- 不因普通增删监听重绑微信客户端。

## 十二、状态与用户提示

系统只能展示可证明的状态：

- “符合当前过滤规则的未读已获得扫描机会”；
- “消息已发现并写入 SQLite”；
- “监听窗口可用或正在恢复”；
- “tail 补洞正常或待重试”；
- “扫描完整或深度覆盖降级”；
- “回复仍在15分钟有效期内或已经过期”。

`GetNextNewMessage` 返回空只表示当前瞬间没有符合过滤规则的下一条消息。启用免打扰过滤时，不能显示“全部未读已100%补收”。

## 十三、明确不采用

本轮不采用以下机制：

- 启动时先给所有未读好友建窗；
- 全部补收完成后才开始回复；
- 固定“扫描一次、回复一次”的1:1配额；
- 双通道期限优先级调度器；
- 每会话独立建窗线程；
- 第二套待答消息队列或 JSON；
- 独立补洞任务队列；
- 通过提高 wxautox 30条/10秒默认参数掩盖截断；
- 普通失败重绑整个微信客户端；
- 并行执行多个通用 wxautox UI 调用。

## 十四、第一阶段验收标准

第一阶段实施完成后至少持续覆盖以下自动和实机场景：

1. 100个模拟未读会话，已有监听好友持续产生 UI 任务，扫描和回复均不能无限饿死。
2. 25条混合消息在10秒上限内只返回23条时，能够识别并显示深度覆盖降级，不宣称完整。
3. 30条和超过30条积压命中数量或时间上限时不会静默丢失，日志包含预期数、实际数、耗时和原因。
4. 先扫描后建窗；任何路径都不能在保存未读前调用 `AddListenChat`。
5. 同一会话并发请求建窗，底层最多执行一次有效 `AddListenChat`。
6. 建窗成功后只生成一个补洞代次，重复验证不重复补洞。
7. 补洞执行期间窗口再次失效恢复，旧成功结果不会清除新代次。
8. 普通 `tail` 补洞不深滚；两次 `GetAllMessage` 不回放旧 callback，重复执行不重复写入。
9. SQLite批次提交失败后扫描停止并显示降级，不继续吞掉微信未读。
10. 持续繁忙数小时，窗口恢复和清理保持低频、限量，不形成连续长时间 UI 阻塞。

## 十五、最终结论

最小修复不是“启动时把所有未读好友先建成子窗口”，也不是提高 wxautox 单次扫描上限。正确方案是：

```text
用一个不会饿死的全局扫描泵先保存未读事实
-> 用现有 supervisor 按需建立长期监听窗口
-> 用带代次的 tail 状态修复所有监听不可信期间的可见尾部
-> 对已确认深度截断只暴露覆盖降级
-> 沿用现有会话 AI 和 UI owner 投递流水线
```

这套结构在不增加通用调度框架和重复消息真源的前提下，第一阶段处理：未监听好友长期排队、建窗吞掉未读、截断静默无提示、所有监听不可信期间的可见尾部缺口和重复建窗竞态。第二阶段按 9.2 的单次 50 条读取、唯一序列对齐和 SQLite gap 状态实施；在跨入口哈希与连续重复气泡实测通过前，继续只显示覆盖降级。
