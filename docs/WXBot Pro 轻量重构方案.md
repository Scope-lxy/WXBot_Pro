# WXBot Pro 轻量重构方案

> 状态：核心调度与恢复代码已落地，自动测试和现有专项实机验证通过；最终验收仍缺 2 小时生产压力和通讯录期间由另一端触发的真实入站回调组合，不能视为 26 项全部完成。

## 落地证据

- 自动测试：当前完整回归通过 `573` 项。
- 停机补洞：从验收前备份恢复本地 history 后，原样 `打开软件.bat` 启动最终代码，由另一端发送新触发消息。当前可见快照按微信顺序补入 `测试一下`、两条相同文字、人工 self、上一轮触发及回复；已存在的旧回复保持 1 条，本轮触发保持 1 条，补洞临时时间标记落盘数为 0。修复前的错误 history 已单独保留为故障证据。
- 通讯录：回顶修复后 50 人连续三批约 `42.114 / 44.538 / 49.234s`；稳定身份协议复测三批约 `43.757 / 46.956 / 51.970s`，8 个资料字段完整返回。每批从顶部精确名称定位后核验稳定身份；真实尾部 5 条虚拟重复行按相同微信号去重为 1 人。生产 `n=2` 尾部探针实测 `98.417s` 后返回原始 2 行相同微信号、去重后 1 人且未修改正式档案；只有取得这类稳定身份凭据才确认完整轮结束，单行、异常或超时不会误报完成。
- 通讯录并发探测：已有子窗口快照约 `4.06s`，证明内核具备有限并行能力，但生产明确不采用；生产 owner 的 50 人批次使用全屏障，后到语音保持未开始，恢复聊天页后约 `5.97s` 发送成功，并由窗口末尾 `self + voice` 复核。
- 关系全量扫描：修复前因每次滚动人为等待 1 秒，`262` 次滚动读取 `1201` 个会话耗时 `277.28s`；删除这项旧分片方案遗留等待后，同为 `262` 次滚动读取 `1202` 个会话在 `14s` 完成，状态保持 `completed`，watchdog 超时 `0`。
- 面板：桌面 `1440×900`、手机 `390×844` 通过；同级字段说明一致，无横向溢出，无 CLI 卡片、无通讯录人数 / 完整轮间隔控件、无全量扫描停止按钮。
- 恢复：语音、文件、转发和 quote 使用持久化投递账本；私聊与群聊 `ai_started` 入站可在重启后重新排队，`send_started` 重启后转为 `uncertain` 且不自动重发；消息定位、联系人档案、关系状态和聊天记忆已有原子写入或有限历史兜底测试。
- 卡死链路：轻操作 / 独占操作 / 通讯录分别按 `30 / 180 / 300s` 边界处理；专用退出码 `86` 和用户主动停止抑制自动启动已有故障注入。原样 `打开软件.bat` 隔离集成测试确认连续 4 次返回 `86` 时只允许前 3 次重启、第四次停止，普通退出码只运行一次。
- 队列等待：调用方不再使用固定 `190s` 等待上限；通讯录期间排队的独占任务等待恢复后完成，故障注入确认不会提前报错后晚到执行，且只投递一次。`30 / 180 / 300s` 只负责识别当前动作卡死。
- UI 旁路：对抗审查发现并删除监听恢复时在业务线程重建原始 `WeChat` 的路径；现在 `REBIND` 只在 owner 内执行。自动边界测试确认只有 owner runtime 和通讯录 worker 能构造 `WeChat`，实机重建后身份、监听和窗口读取均正常。
- 进程退出矩阵：文件、语音、quote、转发、动作组、定时、朋友圈、素材、好友申请、新好友接受和资料修改共完成 `33` 个隔离子进程强退场景；调用前保持 pending / 无提交，调用中冻结 uncertain 或重读微信真源，成功落盘后保持 done / executed / success / sent。

当前不能宣称完成的证据：至少 2 小时生产形态压力测试；通讯录运行期间由另一端真实发来的私聊 / 群聊文字回调，以及图片 / 入站语音描述进入独占后续的接续。

## 一、改造后的用户体验

这次重构不追求增加功能。最高目标是回复对象和内容正确、history / 会话记忆可信、通讯录与营销任务完整执行，以及微信 UI 卡住后能够自动恢复。几分钟回复延迟是可接受的代价；错回复、错图片、重复发送、任务被打断和记录污染不可接受。

改造完成后，用户能感知到的变化应当是：

- 通讯录维护从采集子进程启动到 `SwitchToChat` 恢复完成实行全屏障：不读取或发送聊天消息，不下载图片，不重读语音，也不提前运行 AI、TTS 或写 history。后到任务按原顺序等待，恢复后再继续。
- 任何已经开始的微信任务都是当前最高优先级。发送、转发、素材读取、朋友圈、关系扫描、资料修改、新好友、监听维护和通讯录完成前，后到图片 / 引用下载及其他微信操作都不能插入。
- 手动全量关系扫描连续执行到自然末尾；通讯录批次自然结束或达到自身 300 秒硬超时并恢复后，排队任务先于下一批维护。两者都不为了缩短回复延迟而开放穿插。
- 入站语音有正文时立即处理；只有时长时，只在首次发现后约 5 秒和累计约 10 秒各普通重读一次，仍无正文才静默忽略。
- AI 需要用语音回复时，如果通讯录批次已经开始，则等待当前批次自然结束后再生成和发送；不打断维护，也不无条件降级为文字。
- 手动介入某个对话后，人工发送的 self 消息会自动补入本地历史，下一次 AI 回复能够理解人工已经说过什么。
- 点击停止后，面板立即显示“正在停止”，不再让一次卡住的 `StopListening()` 阻塞 HTTP 请求几十秒。
- 面板减少一批需要用户理解底层实现、但实际没有稳定收益的开关和数字输入。

## 二、故障证据能确认到什么程度

### 2.1 白天旧故障

故障日志能确认问题存在，但不能把根因 100% 归到某一个调用：

- 08:59:57 收到停止请求，机器人主循环当时已经退出，但直到 09:00:50 才完成停止，说明 `StopListening()` 实际阻塞了约 53 秒。
- 09:01 重启后，消息接收和回复至少持续到 09:40 左右，不能简单认定“九点以后完全没有回复”。
- 日志中大量出现“微信 UI 正忙，已进入延迟发送队列”，说明当前一把全局锁会把所有对话、维护任务和发送动作串成一个长队。
- wxautox 日志显示新消息仍在到达，但业务处理和发送有时成批延后；当前日志没有记录“哪一个线程在何时取得了锁、正在执行哪个 wxautox 调用”，因此无法从现有证据唯一定位当时的持锁者。
- `msg.to_text()` 没有超时参数，确实具备永久不返回的风险，但现有日志不足以证明它就是本次卡死的唯一根因。上游同样同步调用它，也不能反向证明它一定安全。

因此，本次方案不围绕某个猜测打补丁，而是直接消除四个结构性条件：多条 UI 路径竞争、锁边界不清、调用无截止线、故障后无法自动恢复。微信 UI 的保守串行是正确性选择，不是需要消除的问题。

### 2.2 7 月 10 日晚间新故障

20:00 之后的应用日志、wxautox 内核日志和本地会话记录形成了比白天故障更完整的证据链：

- 机器人没有从 20:00 开始停止回复。内核日志在 20:00 之后记录了 343 次文字发送调用，22:18 的朋友圈点赞任务也完整执行并关闭；20:16 的一次 `GetAllMessage()` 虽耗时 20.1 秒，但随后已经恢复。
- 真正的硬分界在 22:46。JAY亮 的三段回复分别在 22:46:27、22:46:36 和 22:46:43 发出，第三段也已经写入本地会话记录，证明最后一次 `SendMsg()` 已经返回，不是它永久占锁。
- 22:46:35，全局入口收到 B-吉祥杨 的 44 秒语音。应用层拿到的内容只有“语音44秒”，但同一时刻的内核日志已经读到转写正文；随后连续出现 4 次“控件失效，解析消息失败”，并在 22:46:45 打开该联系人的子窗口。
- 当前生产代码遇到“只有时长”的语音时，会立即在全局微信 UI 锁内同步调用原消息对象的 `msg.to_text()`；该调用没有截止时间。B-吉祥杨 当晚这条语音没有写入本地记录，22:46:54 其他回复仍报告 UI 锁忙，此后微信收发日志全部停止。
- 00:40:40 收到停止请求后，主线程没有立即退出；直到 00:43:12 另一个子窗口收到新消息，微信调用才继续返回，00:43:32 主线程退出。这个现象与 UI 自动化调用一直等待、被后续 UI 事件唤醒一致。
- 22:18 后没有通讯录维护、关系扫描、素材转发、定时消息、备注或标签任务启动记录，因此这些模块不是本次 22:46 卡死的直接触发者。

在没有事发线程栈的前提下，无法从日志形式化证明 Python 当时精确停在 `converter()` 的哪一条机器指令；但排除最后一次 `SendMsg()` 后，时间顺序、锁状态、语音未落盘和失效 Message 对象四项证据一致指向：**本次卡死的高概率直接原因，是对失效的入站语音 Message 对象同步调用 `to_text()` 后长期不返回，并在调用期间持有全局 UI 锁。** 这次证据进一步支持本方案既定决策：生产路径删除 `to_text()`，只在 5 秒和 10 秒通过普通 `GetAllMessage()` 重新读取消息快照。

## 三、方案依据

### 3.1 官方与上游

- wxautox 官方 [WeChat 文档](https://docs.wxauto.org/docs/class/WeChat.html) 明确提示不要在 `GetNextNewMessage` 回调里发送消息。
- 官方 [Message 文档](https://docs.wxauto.org/docs/class/Message.html) 说明：`id` 在切换 UI 后会变化；`hash` 切换 UI 后通常不变，但可能重复；`VoiceMessage.to_text()` 没有超时参数。
- 官方 [Chat 文档](https://docs.wxauto.org/docs/class/Chat.html) 中，`GetAllMessage`、`SendMsg`、`SendFiles` 没有调用截止时间，`SendAudio` 也只有重试次数，没有进程级截止线。
- 当前 wxautox4 版本为 `40.1.15`。
- 上游 `SiverKing/SiverWXbot_plus` 当前核对提交为 `0d8c871f3ed4ceee35984028b8191981a001f7c2`。上游更稳定的主要原因是功能、线程和共享状态更少，不是因为它已经解决了 UI 调度；其回调内同步 `to_text()` 的路径不应照搬。

### 3.2 本机实测

完整数据见 `docs/微信 UI 并发实测结果.md`。对方案最重要的结果是：

| 场景 | 结果 |
| --- | --- |
| 单路子窗口读取 | 约 3.1 秒 |
| 两路子窗口读取 | 约 6.2 / 6.9 秒，均成功 |
| 三路子窗口读取 | 约 10.3 / 12.0 / 12.3 秒，严重退化 |
| 通讯录 + 一路子窗口文字 | 文字约 1.2 秒，均成功 |
| 通讯录 + 两路子窗口读取 | 读取约 9.6 / 10.5 秒，均成功但明显变慢 |
| 通讯录 + 语音 / 文件 / 主窗口历史 | 出现通讯录不返回或控件超时，不允许重叠 |
| 终止 50 人通讯录子进程 | 约 0.34 秒，随后切回聊天、重建子窗口、收发均成功 |

这证明微信 UI 不是单通道，但也不是任意多通道。进一步看吞吐，两路子窗口读取并发的总完成时间约 `6.9s`，顺序执行两次按基线约 `6.1s`；两路文字并发相对顺序执行也只节省约 `0.3s`。实测真正有运营价值的并发是“长时间通讯录采集 + 一路已有子窗口轻操作”，不是让两个通用聊天 worker 长期并发。

## 四、唯一的 UI 调度规则

不建立通用任务编排框架，也不保留两个通用 UI worker。直接改造现有 `core/wechat_ui_actions.py`，只创建一个专用 UI owner 线程；通讯录最小子进程是唯一允许与它并发操作微信的例外。

### 4.1 执行主体与边界

1. **UI owner 线程**：初始化 COM、创建并独占 `WeChat()`，其事件循环只执行监听、读窗、发送、主窗口、朋友圈、资料编辑和直接 UIA 操作。
2. **通讯录子进程**：只执行一次 `SwitchToContact -> GetFriendDetails(50)`，写临时结果后退出；owner 不阻塞等待，而是在事件循环中轮询 PID、结果和 300 秒截止时间。
3. **现有机器人主循环和业务线程**：继续做任务到期判断、AI/TTS、消息合并和本地数据处理，但只能提交纯数据意图，不能持有或访问微信对象。

实测证明通讯录运行时操作一个已有子窗口在当前版本可行，但生产不再使用这项并发能力。正确回复、可信 history/记忆和当前运营任务完整结束优先于几分钟回复延迟；通讯录批次建立统一屏障，删除轻量穿插产生的分类、越过和升级边缘逻辑。

### 4.2 通讯录批次使用全屏障

所有进程内微信动作始终进入 UI owner 的同一条 FIFO。通讯录子进程启动后，owner 不再消费任何聊天读取、发送、图片下载、语音重读、监听维护或其他微信 UI 意图；消息业务线程也停在同一个屏障前，不提前调用 AI。批次完成或达到 300 秒硬超时后，先执行 `SwitchToChat` 恢复，再按 FIFO 处理积压消息和任务。

普通回调只复制 wxautox 已给出的标量并入队，不发送、不读取控件树。图片和引用是唯一的线程绑定例外：回调先向 owner FIFO 申请执行时段，获准后在原回调线程调用原消息的 `download()` / `download_quote_image()`，完成后只把路径标量入队；原 Message 不进入 owner 或业务线程。这个策略有意接受几分钟回复延迟，换取不猜图片、可靠 history，以及任何已开始的微信任务都不会被后到媒体下载破坏。

### 4.3 一条 UI 意图队列

- UI owner 是唯一消费者；业务线程、定时任务和 Web 请求只提交纯数据意图，不直接调用微信。
- 已经开始的动作永远先完成。这个非抢占规则适用于发送、转发、素材读取、朋友圈、关系扫描、资料修改、新好友、监听维护和通讯录等全部微信任务；后到的图片 / 引用下载也只能进入 FIFO，不能插入当前任务中间。通讯录屏障期间进一步暂停消息业务线程；结束并完成 `SwitchToChat` 恢复后，按原队列顺序继续。
- 通讯录启动也通过 owner 决定：先完成一轮到期的 `GetNext/GetListen`，确认没有业务独占动作正在执行或等待后再启动。周期轮询本身不永久阻止后台维护；因为开始、完成和队列状态都由一个 owner 修改，不再需要“检查空闲后再抢容量”的原子锁。
- 通讯录期间后续周期轮询只合并成一个 poll-due 标志，避免积累无意义调用；聊天回调消息由纯数据 FIFO 保存。恢复后不设计多级优先级。`IsOnline` 占不到执行时机就跳过本轮，不能据此判离线。
- 批处理每次只提交一个最小事务：一条定时内容、一个素材批次或一个联系人修改。手动关系全量扫描是例外，它是用户明确触发的一次连续独占事务，不在滚动间隙穿插其他 UI 动作。
- 面板触发的微信动作立即返回“已排队/执行中”，继续复用各模块现有状态和进度轮询，不让 Flask 请求等待微信数十秒。

UI 事务不一定等于一次方法调用。普通 `SendMsg()` 本身就是一个事务；朋友圈的“打开编辑器 -> 发布 -> 验证 -> 关闭”和单个联系人的“定位 -> 校验 -> 修改 -> 清理”必须保持完整，不能在中间让其他动作切换 UI。AI、识图、TTS、文件准备和人类化等待全部在事务外；只有维持当前编辑器状态所必需的短等待留在事务内。

### 4.4 同一会话顺序不再依赖锁

真实发送已经由唯一 owner 串行，因此删除 `_chat_send_locks` 和 `_WechatActionLockedChat`。每个待发意图只携带：会话 key、会话版本、来源、内容、是否可替换、任务/取消版本。

- AI 回复、识图回复和 TTS 语音属于可替换意图。新入站或人工 self 推进会话版本后，尚未开始的旧意图直接失效。
- 定时/随机消息、关键词、管理员明确命令、新好友欢迎和用户确认的任务属于独立业务动作，按入队顺序执行，不被普通新消息取消。
- 私聊 AI 拆分后的每个气泡是一个独立可取消意图；气泡间的人类化等待在 owner 外完成，每个气泡开始前都由 owner 复核会话版本。新消息或人工 `self` 到达后，已开始的单个气泡发完，尚未开始的剩余气泡全部取消。
- 轻发送发现子窗口不存在时，把同一意图转为“AddListenChat -> 重新定位 -> 原发送”的独占依赖链，并保留原会话顺序位置；后到的同会话动作不得超车。
- owner 在真正调用微信前再校验会话版本、任务版本、取消状态和最新 `contact_key -> send_name`；不再存在 UI 锁、会话锁、容量锁之间的嵌套或升级。

继续复用现有同会话消息合并管线：每个会话最多一个正在生成批次和一个待合并批次。outbound echo、系统时间和系统提示不推进版本，人工 self 与对方新消息推进版本。机器人发送的 history 以真实 `self` 回调为顺序真源；已主动落盘的普通回复只去重，不重复保存。素材组合发送缺失回调时由成功发送记录补写，素材和附加文案都缺失时按“素材在前、附加文案在后”兜底。

### 4.5 对象归属

- 原始 wxautox client 只允许 UI owner 访问；业务层 `bot.wx` 只能是提交纯数据意图的 `UIClientFacade`，状态页直接使用启动时保存的纯字符串 `wx_id`、`nickname` 和状态快照。
- wxautox 回调只复制会话名、类型、方向、发送者、内容、时间、运行时 `id/hash/hash_text` 和窗口顺序，记录收到时间并入队；不读取控件树、不发送、不补洞、不调用 `to_text()`。运行时 id 只用于当前进程的回调去重，不写入 history，也不作为跨重启补洞锚点。图片 / 引用按上一节的 owner FIFO 预约在原回调线程下载，原对象不跨线程。
- 在现有 `core/message_pipeline.py` 定义两个小型纯数据记录 `ConversationRef` 和 `MessageEnvelope`，保留业务代码常用的 `.who/.chat_type/.content/.type/.sender` 读取方式，但不提供任何微信方法；避免为对象隔离重写整条 AI 业务链。
- 普通 owner 队列只接受枚举化 `UIIntent(kind, payload, conversation_version, task_version)`，payload 不接受 callable 或微信对象。唯一例外是线程绑定的实时图片 / 引用下载预约：callable 只在原回调线程执行，owner 只授予 FIFO 时段，不读取或缓存其 Message。
- 朋友圈、备注、好友申请等低层适配器可以留在现有 feature 文件，但入口先执行轻量 `assert_ui_owner_thread()`；配合静态扫描，错误线程调用在开发和测试阶段立即失败。
- Chat、Message、NewFriend、Moments、SessionBox 和窗口组件不能进入业务线程、普通 owner payload、缓存或持久化记录。实时图片 / 引用 Message 只允许留在原回调栈内，取得 owner FIFO 时段后立即下载并丢弃。
- owner runtime 的 `_listen_chats` 只在 owner 线程缓存原始子窗口，重绑时由同一线程整体清空；业务层监听缓存最多保存只有会话身份和 owner 引用的 `OwnedChat` facade。`_material_runtime_messages` 不再保存 Message，只保存素材稳定签名和来源描述。
- 实时入站图片 / 引用使用回调原对象申请 owner FIFO 预约时段；只有排到队首且当前动作已经完整结束后才下载，不事后重定位，也不按媒体类型抢占。其他 quote、素材转发等主动操作仍在 owner 内读取当前窗口并唯一定位。固定上限的近期历史读取只用于主动操作，不恢复无界滚动；仍定位不唯一就跳过危险动作并记录。
- 新好友接受事务重新读取候选并唯一定位，不跨事务保存 NewFriend 对象；重名或信息不足时不猜测。

是否纳管以“最终是否操作微信界面”为准，包含 wxautox、直接 UIA、wxautox 窗口组件和 Win32 微信操作。

启动时先由 owner 完成 `WeChat -> GetMyInfo -> StartListening -> 固定监听注册` 并返回纯身份/监听快照，业务层再做账号目录迁移、记忆初始化和任务注册。重绑同样只替换 owner 内对象和缓存，但普通业务失败不得触发重绑；监听器异常先用现有客户端重建监听，只有 Windows 无效窗口句柄、COM/RPC 断开等证据确认后续微信任务无法继续时才重绑。整机停止时先拒绝新意图；整机停止属于当前通讯录任务自身的取消边界，可以按 PID 终止子进程，随后由 owner 执行 `StopListening`。通讯录页面的“暂停维护”只阻止下一批，当前批次继续完成；普通后到业务任务同样无权终止通讯录。

### 4.7 明确不进入 UI 队列的工作

AI/TTS/视觉接口与测试、Prompt 和配置管理、TTS 试听、本地记忆/聊天记录、任务时间计算、素材筛选、文件准备/选择、缓存清理、备份和账号迁移、运行统计、邮件/Webhook、Siver 面板连接、面板账号与安全都不操作微信，继续在各自现有线程或请求中运行。wxautox 授权检查和内核更新也不进入 UI 队列，但内核更新只能在机器人停止状态执行。UI owner 不能被误用成新的全局业务锁；JSON 仍由各数据域自己的锁和原子替换保护。

## 五、通讯录自动维护

通讯录仍是基座能力，不删字段、不降级成昵称列表。

### 5.1 固定策略

- 自动维护固定每批 50 人，删除 `20 / 50 / 80` 三档和对应配置分支。
- 完整轮间隔按现有默认值内置为 7 天，不再暴露配置字段和面板控件。
- 每批最低间隔和允许维护的时间窗口继续允许用户自定义；面板只保留自动维护开关、每批维护间隔、维护开始时间和维护结束时间。
- 继续采集当前 v2 通讯录的全部真源字段。固定 50 只改变每批人数，不改变每个人读取的详情。
- 手动立即建档、备注修复、身份校准继续保留。
- 一批成功后才原子合并；失败、超时或用户停止时不覆盖正式通讯录。
- 只有完整一轮确认到达尾部后，才允许处理本轮未出现联系人的失效状态。

### 5.2 非抢占运行规则

通讯录采集继续只在 `feature/contact_auto_collector_worker.py` 最小子进程中运行。UI owner 启动后登记 PID、截止时间和 `contact_active`，随后立即回到自身事件循环，不同步等待子进程结束。

通讯录批次从启动到 `SwitchToChat` 恢复完成均为全屏障。已有子窗口读取、上下文可见补洞、入站语音 5/10 秒重读、图片下载和普通文字回复全部排队，不与采集并行。

通讯录运行期间，所有后到微信 UI 请求都进入等待队列，不维护“轻量可穿插”白名单。包括已有子窗口读写、新会话 `AddListenChat`、全局 `GetNextNewMessage`、监听巡检/重建、客户端重绑、图片/引用下载、语音重读、文件、素材转发、朋友圈、备注/标签、关系扫描及新好友操作。

这些请求不能调用 `kill`、`taskkill` 或 `StopListening()` 打断通讯录。当前 50 人批次自然完成后，owner 先执行 `SwitchToChat` 恢复，再执行等待最久的独占动作；只有独占队列清空且到达正常维护间隔后，下一批通讯录才可以开始。

通讯录开始、独占队列和 `contact_active` 都只由 owner 修改，因此无需额外准入锁。如果独占动作已经排队，通讯录不能抢先启动；一旦子进程开始，后来到达的独占动作必须等待。父进程仍保留 300 秒硬超时和用户主动停止能力，但这是当前动作自身的故障/停止边界，不是后续任务的抢占权。

### 5.3 数据完整性

保留现有 `contact_key`、`wechat_id`、`wxid`、`nickname`、`remark`、`region`、`source`、`added_at`、`signature`、`tags`、`status`、`warnings` 以及身份和关系状态字段。

`display_name`、`send_name`、`send_target` 仍然只是任务运行时快照，不写回联系人真源。这是数据职责边界，不是本次删减字段。

## 六、入站语音

生产路径彻底删除 `to_text()`，只读取 wxautox 正常返回的 `message.content`。私聊和已开启语音识别的群聊使用同一套兜底；群聊匹配时额外保留发送者，不能把不同群成员的同长度语音合并。

固定流程如下：

1. 首次收到语音时，正文已经存在：立即按普通语音消息处理。
2. 只有“语音 N 秒”而没有正文：登记为该会话的一条待确认语音，不阻塞回调和其他会话。
3. 首次发现后约 5 秒，通过该会话普通 `GetAllMessage()` 做第一次新快照；找到正文就立即处理。
4. 累计约 10 秒，再做最后一次普通 `GetAllMessage()`；仍无正文才静默忽略。
5. 同一私聊或群聊同时有多条待确认语音时，共用这一时刻的一次窗口快照，不为每条语音各读一次。

`hash` 只用于缩小同一窗口里的语音候选，不能用于全局身份、排序或去重。因为实测存在多条相同文件或相同时长语音共享一个 hash。最终按方向、群聊发送者和窗口顺序，把候选依次匹配给该会话的待处理队列。

这套策略最多两次重读；如果第一次快照已出现正文，第二次任务立即取消。

## 七、出站语音回复

“当前已有子窗口只能轻量发文字，但回复策略命中了语音”时，按下面处理：

1. AI 生成和 TTS 合成先在 UI owner 外完成，不占用微信。
2. TTS 成功后创建该会话的可替换语音意图，记录当前会话版本并进入唯一 UI 队列；等待期间不持有任何 UI/会话锁。
3. 若通讯录正在运行，语音作为独占动作等待当前 50 人批次自然结束；owner 不处理已有子窗口读取、其他会话普通文字或任何后到微信 UI 请求。
4. 通讯录结束并恢复聊天页后，这条语音先于下一批后台维护执行；owner 调用前再次核对会话版本，仍是最新版才通过已校验子窗口执行 `SendAudio()`。
5. 如果等待期间同一会话出现新消息或人工 self 接管，旧语音在尚未调用 `SendAudio()` 时可以被原子取消；释放临时音频，不再占据发送顺序。

降级规则必须按“微信调用是否已经开始”区分：

- TTS 失败、音频文件无效、尚未进入 `SendAudio()`：可以安全降级为文字。
- `SendAudio()` 明确返回失败，且可见窗口确认没有新增 self 语音：降级一次文字。
- `SendAudio()` 已经开始后超时或进程退出：先进入不确定发送恢复，不能立即再发文字或重发语音。

恢复后读取该会话一次可见窗口。如果发送前锚点之后已经出现 self 语音，则视为已送达；确认没有出现时才降级一次文字。无法确认时宁可记录一次待核对结果，也不自动双发。这里复用现有发送回声账本，不引入跨账号全局消息 ID。

### 7.1 同一会话在等待期间又产生新回复

同会话顺序不是“所有已经生成的内容都必须发送”，而是“真实发送不能乱序”。以实际调用 `SendAudio()` / `SendMsg()` 为提交点：

- 提交前：回复只是可替换的待发意图。新入站消息推进现有会话序号，旧语音版本失效；新的文字回复可以替换它并由 owner 发送，不能同时保留旧语音。
- 提交后：已经开始的微信 UI 发送不可取消。新文字必须等当前发送返回，再按最新会话状态决定是否仍需发送。

替换回复必须覆盖“上一次成功发送之后尚未回复的全部入站消息”。如果已经生成的新文字没有覆盖这段完整消息，就同时丢弃旧语音和这条不完整文字，合并未回复消息后只生成一次。实现只复用现有每会话消息序号，不增加全局消息 ID 或新的调度模块。

## 八、上下文自动补洞

补洞的目标不是“修复一个窗口”，而是保证下一次 AI 请求前，本地历史包含微信可见的人工和对方消息。

### 8.1 触发条件

只在有明确理由时读一次可见窗口：

- 启动后该会话第一次进入 AI；
- 动态子窗口新建、恢复或重建后第一次处理；
- 消息回调或本地写入发生异常；
- 当前入站消息在本地历史尾部找不到；
- 检测到人工 self 消息但本地没有保存。

不做周期巡检，不自动滚动历史，不提供“手动修复某个窗口”入口。

### 8.2 写入规则

- 当前可见窗口是事实来源。锚点只表示本地与微信是否已经对齐，不限制补洞范围；有锚点时，锚点前后所有本地缺失消息都补入。
- 无锚点表示旧尾部已超出读取范围，此时把过滤后的当前可见快照作为新的历史尾部；无论本地 history 是否为空，都不能因此放弃停机期间仍可见的对话。
- wxautox4 原生 `message.id` 只在当前客户端快照内稳定，重建客户端后会变化；它不写入 history，也不作为跨重启锚点。相同图片的 hash 也不能区分气泡。
- 普通气泡继承前一个 `TimeMessage` 的时间并保持窗口顺序；可见前缀没有时间分隔时，以当前触发消息时间为尾点向前保持顺序。微信明确给出的分隔时间可参与邻近时间匹配；为排列推算出的时间只决定插入位置，必须再按方向、类型和内容一对一抵消已有气泡，临时推算标记不落盘。日期解析兼容 `YYYY-MM-DD` 与 `YYYY/MM/DD`，history 统一写后者。私聊按方向、类型、规范化内容和邻近时间逐次匹配，群聊额外包含发送者；每条本地记录最多抵消一个可见气泡。
- 两条合法的 `OK`、表情、相同问候或相同图片按出现次数保留。10 分钟窗口只用于把微信时间分隔与本地精确秒数对齐，不能用一条本地记录吞掉多条重复气泡。
- 只补入，不删除、不覆盖已有历史；当前触发消息已经由正常入站链路保存时，补洞匹配并跳过它。快照比较、补差额和写盘在同一把会话记忆锁内完成，同一快照重复执行不得重复写。未识别语音占位不写入模型上下文。
- 人工 self 消息和对方消息同等处理，并推进该会话本地顺序。

补洞与“保存聊天记录并带入 AI 上下文”是同一个能力，不再暴露“低风险补洞 / 允许滚动补洞”两个技术开关。

## 九、卡死恢复与停止

### 9.1 调用截止线

UI owner 在共享运行快照中记录当前 wxautox 动作、会话、开始时间和截止时间。现有面板进程只增加一个最小监控线程读取该快照，不为每个模块建立 watchdog。

- 轻操作固定 30 秒截止线。
- 非通讯录重操作固定 180 秒截止线。
- 通讯录子进程固定 300 秒硬超时。

通讯录超时只终止采集子进程。其他 wxautox 调用超过截止线时，Python 无法安全杀死单个卡死线程，因此监控线程先记录当前动作和全部线程栈，按已登记 PID 终止通讯录子进程树，再以专用退出码强制退出整个面板进程，不能依赖 `finally` 清理。

`打开软件.bat` 只对这个专用退出码自动重启；采用滚动时间窗口记录恢复次数，30 分钟内最多自动重启 3 次，第 4 次停止自动循环并明确提示，避免微信环境本身异常时频繁重启。启动时检查上次登记的通讯录 PID 与命令/创建时间，确认仍是本项目孤儿进程才清理，不能只凭可能复用的 PID 直接 taskkill。配置、通讯录和消息状态都已落盘，因此整个进程重启比在半死线程旁继续运行更可靠，也比再引入一个机器人子进程管理层更轻。

### 9.2 停止按钮

`/stop_bot` 设置停止标志并立即返回“正在停止”。UI owner 先拒绝新意图并取消所有尚未开始的排队动作；已经开始的单个动作自然结束后，只允许 `StopListening()` 关闭动作执行。面板轮询最终状态，不同步等待 10 秒或更久；若 owner 已卡住，则由截止监控触发整进程恢复。

若 `StopListening()` 超过重操作截止线，同样走专用退出和自动重启；启动脚本看到这是“用户主动停止”时不应把机器人自动启动，只恢复面板服务。

### 9.3 排队、部分成功与重启恢复

动作截止时间从 UI owner 真正开始事务、即将进入 wxautox 时计算，排队时间单独记录，不能把正常等待误判成 UI 卡死。业务任务必须先落盘为 `pending`，owner 取出并完成最后校验后才写 `inflight`，实际成功后才推进计划。

| 任务 | 最小持久化键 | 进程中断后的处理 |
| --- | --- | --- |
| 私聊 / 群聊 AI | 会话类型 + 会话 + 发送者 + 未答入站尾序号 | AI 生成中断则沿用原记录重新排队；首次真实发送前写 `send_started`，此后中断转 `uncertain`，不自动重发 |
| 关键词 / 管理员文字 | 会话 + 来源消息稳定标识 + 可选回复内容 | 排队前固化纯数据意图；同组多段文字连续发送，实际结果不明时不盲目补发 |
| 语音 / 文件 / quote | 会话 + 本地会话序号 + 类型 + 文件摘要或引用签名 | 只有 self 回声能够唯一匹配时才收敛为成功；无法确认就标 `uncertain`，不自动补发文字或重发文件 |
| 定时消息 | `run_id + target + message_index` | 只恢复未开始项；`inflight` 先查目标窗口回声，不能从第一个目标整批重跑 |
| 素材转发 | `run_id + material_id + target`，另存本次 1~9 人批次 | 正常返回后逐目标落记录；调用中断的整批标为 `uncertain`，不盲目自动重发，避免最多 9 人收到重复素材 |
| 朋友圈 | 任务 id + 预期文案/图片摘要 | `running` 恢复时先检查最新朋友圈；确认已发布则补记成功，无法确认则回到待确认，禁止自动再发一条 |
| 备注 / 标签 | 联系人真源 key + 目标备注/标签 | 重新读取当前资料；已经达到目标就是成功，否则幂等重试 |
| 新好友通过 / 欢迎语 | 候选标识 + 欢迎动作序号 | 重新读取新好友状态；欢迎语用目标窗口 self 回声确认，避免重复欢迎 |
| 主动好友申请 | candidate id + 本轮申请内容摘要 | 重新读取候选/会话状态；无法确认是否已经发出时标 uncertain，不连续重复申请 |
| 关系全量扫描 | 扫描 run id + 已读取数量 + 当前状态 | 中断后标记失败或部分完成；用户再次触发时从顶部重扫，不依赖旧滚动坐标，也不自动续发 UI 动作 |
| 监听增删 / 重建 | 目标窗口名 + 期望监听状态 | 重新读取当前子窗口集合，以实际状态收敛，不按旧步骤机械重放 |

所有模块共用同一条状态语义，但状态仍写回各自现有运行记录，不新增通用数据库：排队是 `pending`，owner 调用前是 `inflight`，明确返回后是 `done/failed`，调用中断且无法确定结果是 `uncertain`。读取类动作可重试；备注/标签等幂等写入先读后重试；发送、好友申请、发圈等非幂等动作不能盲重放。

私聊和群聊进入回复管线时先写入账号级待答记录，并保存会话类型、发送者、时间和内容哈希；只有真正进入 AI 分支才标记 `ai_started`，正常完成后标记 `resolved`。重启时把 `ai_started / replay_pending / replaying` 原子收敛为 `replay_pending`，等待账号、记忆、Prompt 和监听缓存初始化完成后再按 private/group 重新排队；恢复沿用原记录，不创建记录链。首次真实发送前写 `send_started`；重启发现该状态时转为 `uncertain` 并禁止自动重发。`routing` 阶段收敛为未知，避免把关键词、限流或人工接管误恢复成 AI 回复。

只有一个微信接口内部不可拆分的真实动作才作为最小动作，例如一次 quote、一次素材 forward、一次好友资料编辑或一次朋友圈 Publish。quote 后续文字、AI 拆分气泡、关键词多项、新好友欢迎和定时消息都不组成连续动作组：每一项分别等待、复核会话或任务版本、提交并落盘，新消息、停止或配置变化可以取消尚未开始的剩余项。若单项进入微信提交阶段后异常，投递账本把该项标为 `uncertain`，尚未开始项保持未执行。owner 在真实微信动作前复核任务版本，并按 `contact_key` 解析当前发送名，任务已变化、联系人已失效或身份不唯一时取消，不能回退到历史昵称猜测目标。

素材转发的 `uncertain` 采用“宁可少发一次，不自动重复打扰”的口径，并在任务记录中单独统计；正常路径仍保留最多 9 人一批的性能。若以后要求严格逐人确认，只能改成单目标转发或逐窗口核验，这是明确的性能/确定性取舍，不应隐藏在自动重试里。

运行快照中的联系人目标保存 `contact_key` 和当时显示名，但真正发送前必须用 `contact_key` 从最新通讯录重新解析 `send_name`。排队期间备注已变化时发送到新备注；联系人已失效或无法唯一解析时跳过并记录，不能拿历史名称猜测目标。手工输入且没有 `contact_key` 的目标只允许按原精确名称执行。

### 9.4 启动与测试实例清理

正式交付只认 `打开软件.bat` 启动链。最终运营状态必须只有一个面板进程树和一个机器人 runtime，不能把自动选择到 `10002` 或更高端口的第二面板当成已经替换了仍在 `10001` 运行的旧机器人。

本任务启动临时面板时，测试工具必须在启动前记录既有监听端口和进程，启动后保存本次启动器、Python 包装进程、实际服务进程和端口。验证结束后只终止这组已确认属于本次测试、且 `bot_running=false` 的进程树，并复核端口释放、原正式实例状态未变化。若测试实例已经启动机器人，必须先经 `/stop_bot` 等待正常停止；不能直接强杀仍持有 wxautox 监听的面板来追求自动清理。

这条约束属于验收纪律，不增加面板上的实例管理开关，也不引入常驻外部 supervisor。生产的卡死恢复仍由专用退出码 `86` 和 `打开软件.bat` 的 30 分钟三次滚动限制负责。

| 处理 | 项目 | 收益与代价 |
| --- | --- | --- |

| 删除 | 随机朋友圈点赞 | 删除低价值主窗口任务和误点赞风险；代价是失去随机账号活跃行为，朋友圈发布任务仍保留 |
| 删除 | 通讯录 `20 / 50 / 80` 三档、完整轮间隔控件 | 内置固定 50 人 / 7 天，减少配置和测试矩阵；自动维护开关、每批最低间隔和维护时间窗口保留 |

| 保留 | 自动转发、素材转发、定时/随机消息、新好友管理、朋友圈发布 | 运营结果不变，只统一经过 UI owner |
| 保留 | 私聊/群聊识图、关键词、文字/语音回复、拆分回复、每日启停 | 这些配置会产生真实运营差异，不属于技术噪声 |

关系全量扫描失去 CLI 后会占用主窗口，但实机一次完整扫描通常是几十秒到几分钟。用户手动触发后，owner 先回到会话列表顶部并连续滚动到自然结束，中间不插入回复，也不允许手动停止。连续 8 次无新增视为末尾；1000 次仅防无限循环，命中时标记 `partial`，不能谎报完成。

全量扫描滚动后立即读取下一屏，不增加固定逐屏等待；只在开始和结束回顶后各等待 1 秒稳定界面。自动短扫描在全量扫描运行期间不得提交，owner 返回后必须重新加载最新关系状态再合并，禁止用排队前旧快照覆盖全量扫描的 `completed` 结果。

## 十一、实施顺序

### 阶段 1：统一 UI 边界

- 把现有 `wechat_ui_actions` 改成由单个专用 UI owner 线程消费的一条纯数据意图队列。
- 给全部真实 wxautox、直接 UIA 和窗口组件操作分类，移除绕过入口。
- 把事务边界从“整个模块/整个批次”收缩为最小不可交错单元，删除 UI 锁、会话发送锁、旧 chat/message 包装器和嵌套申请。
- 管理员、接管、定时和 Web helper 只返回或提交纯数据意图；所有 `bot.wx` 访问收口到 owner。
- 把 AI、TTS、文件准备、随机延迟移出 UI 区间。
- 普通回调只入队，不执行回复链；实时图片 / 引用只允许在 owner FIFO 授权时段内原位下载，不做其他业务处理。

验证：静态扫描不再发现 owner 之外的微信 UI 调用；单元测试覆盖 FIFO、通讯录全屏障、恢复、意图替换和同会话顺序；现有全部测试通过。

### 阶段 2：通讯录非抢占调度和语音

- 通讯录固定 50 人 / 7 天一轮，保留可配置的批次最低间隔和维护时间窗口，由 owner 统一决定启动、轮询完成和独占动作接续。
- 入站语音改为 5 秒 / 10 秒两次 `GetAllMessage()`。
- 删除全部生产路径 `to_text()`。
- 出站语音按独占动作处理，并完成不确定发送恢复。

验证：通讯录运行中到达的文字、图片、语音和文件均不开始业务处理或微信操作；当前批次恢复后按到达顺序继续并先于下一批维护；只有时长的语音最多重读两次。

### 阶段 3：补洞与瘦身

- 改成精确时间 / 出现次数匹配，删除 10 分钟近重复抑制。
- 删除 CLI、滚动补洞、随机点赞和低价值面板控件。
- 关系扫描改为手动连续独占：从顶部扫到连续 8 次无新增；heartbeat 只防长事务被 180 秒整体截止误杀。

验证：人工 self、重复短句、相同图片出现次数、时间分隔继承、空 history 初始化、非空 history 无锚点补为新尾部、锚点前缺口补入、当前触发消息不重复、重启恢复、群聊同文不同发送者全部通过；通讯录字段逐项对比无缺失。

### 阶段 4：故障恢复和压力验收

- UI owner 增加当前动作快照、截止记录和线程栈采集。
- 为定时消息、素材转发、朋友圈、新好友和资料修改补齐步骤级持久化与恢复。
- 启动脚本增加专用退出码恢复和次数限制。
- 停止接口改为异步状态。
- 用原样 `打开软件.bat` 验证最终代码加载、单实例运行和退出码恢复；本任务启动的临时面板按已登记 PID 清理，测试结束后不得遗留额外端口或机器人实例。

验证：故障注入能在截止线后自动恢复；停止请求 1 秒内返回；临时面板关闭后端口和进程树均清空且不影响原正式实例；最终版本从 `打开软件.bat` 以单面板、单机器人 runtime 启动；完成至少 2 小时混合压力测试后再投入正式运营。

## 十二、对抗式审查

| 攻击场景 | 原方案可能失败 | 本方案约束 |
| --- | --- | --- |
| 为了利用两路轻并发保留两个通用 worker | 实测几乎没有总吞吐收益，却增加 COM 对象、generation、容量和故障组合 | 只保留一个进程内 UI owner；并发仅来自通讯录专用子进程 |
| 把实测可并发误解成生产必须并发 | 为降低几分钟回复延迟引入越过、升级和多类媒体边缘逻辑 | 并发是优化而非功能；通讯录期间使用一个全屏障 |
| 未实测就让 GetNext/GetListen 与通讯录并行 | 两者可能操作主窗口并破坏联系人扫描 | 保守列为独占；通讯录结束后合并补一轮，专项实测后才允许降级 |
| owner 在通讯录期间继续消费轻量聊天 | 需要维护穿插白名单、升级和媒体特殊路径，增加错回复与 UI 干扰风险 | owner 只轮询通讯录 PID；全部聊天和 UI 意图等待恢复 |
| 把一次方法调用当成完整边界 | 朋友圈编辑器或联系人资料页中途被其他任务切走 | 以最小不可交错 UI 事务为边界，不机械按方法拆锁 |
| 已开始其他任务时允许图片回调直接下载 | 图片操作插入发送、素材读取、关系扫描或资料修改中间，切换控件状态并破坏当前目标 | 图片 / 引用先申请 owner FIFO 时段；当前任务完整结束前不得下载 |
| 保留 UI 锁、会话锁和包装器 | 锁顺序矛盾、语音等待不能被替换、机械换锁仍会自锁 | 唯一 owner 串行真实调用；顺序由意图链和版本负责，删除发送锁 |
| 轻发送发现无子窗口后直接 AddListen | 通讯录期间切主窗口，或补窗后原回复丢失 | 原意图转成独占依赖链，保持同一会话顺序位置 |
| 补窗后把原发送放到普通队尾 | 同一会话后到文字先发，原回复反而最后发 | 补窗依赖链保留原会话顺序占位，后到发送不得越过 |
| 子窗口校验和 SendMsg 拆成两次事务 | 校验后窗口被关闭或改绑，使用失效对象/发错窗口 | owner 在一个事务内重新取得、校验并发送 |
| 通讯录期间继续生成或发送回复 | AI 基于半截会话生成、图片事后错配，或聊天 UI 干扰采集 | 消息业务线程和 owner 使用同一通讯录屏障，恢复后 FIFO 处理 |
| 通讯录刚启动就来语音回复 | 后到语音错误地杀掉正在扫描的子进程 | owner 一旦启动通讯录子进程就视为已经开始，语音只排队，不允许抢占 |
| TTS/AI/人类化等待在 owner 内 | 外部接口或 sleep 拖住所有微信动作 | 全部在 owner 外，只提交准备完成的 UI 意图 |
| `SendAudio()` 卡死但实际已发出 | 重启后再发文字，用户收到两次回复 | 发送后先读 self 回声；不能唯一确认则标 uncertain，不自动降级或重发 |
| 语音等待时又生成文字回复 | 旧语音和新文字都发，或会话锁让新文字永久等待 | 同会话可替换意图按版本收敛为一个；调用开始后不可取消 |
| 同一会话连续消息各自启动 AI | UI 等待期间积累大量过时回复、浪费接口并扩大队列 | 每会话一个生成批次 + 一个合并批次，发送前再校验会话版本 |
| 机器人 self 回声也推进版本 | 刚发送成功的回声把后续合法回复误判为过期 | outbound echo、系统消息不推进版本，人工 self 才推进 |
| 回调不经 owner 直接下载、补洞、to_text 或发送 | 任一慢调用抢占当前 UI，Message 对象又可能被带入业务线程 | 图片 / 引用只在 owner FIFO 授权时段内用原回调对象下载；其余回调只复制标量入队 |
| 周期轮询每轮都进入等待队列 | UI 忙几分钟后积累大量过期 GetNext/IsOnline 调用 | 消息轮询只保留一个合并标志，健康检查失败即跳过 |
| 通讯录结束后忘记补全局轮询 | 黑名单模式的新会话长期未发现 | contact 恢复完成后先消费唯一 poll-due，再继续正常周期 |
| 定时消息整批标记 running 后中断 | 重启后整批重跑造成重复，或旧 running 永久残留 | 按 run/目标/消息序号持久化，只恢复未完成步骤 |
| AI 生成中进程重启 | 尚未形成待发意图，本轮入站永远没人回复 | 持久化未答入站尾序号；重启后合并缺口重新生成一次 |
| 九人素材批次中途失联 | 不知道哪些目标已收到，盲目重试最多重复 9 人 | 批次预写 inflight；异常后标 uncertain，不自动重发 |
| 朋友圈已发布但状态未落盘 | 重启后重复发圈或永远卡在 running | 用预期内容检查最新朋友圈，确认后收敛状态 |
| 备注/标签整批占住 owner | 数十人修改成为一个不可抢占的超长事务 | 每个联系人独立事务，读取目标状态后幂等修改 |
| 新好友处理把列表和 sleep 全包住 | 一个好友欢迎流程拖住后续所有 UI | 接受、资料、每条欢迎消息拆成独立事务，等待在 owner 外 |
| 跨事务保存 NewFriend 对象 | 对象属于旧 COM 线程或已失效，接受错人/调用失败 | 接受事务重新读取并唯一定位候选；歧义时跳过，不猜测 |
| 等待时间计入 UI 截止线 | 通讯录正常运行时把排队语音误判成卡死 | 截止线只从 owner 开始真实 UI 事务时计算，等待时长单独观测 |
| 任务排队后被禁用或配置已变化 | 几分钟后仍按旧目标、旧内容执行 | 事务提交前校验任务版本/取消状态；当前运行使用不可变快照，已取消则不进入 UI |
| 排队期间好友备注改变 | 定时消息或素材仍使用旧 send_name，发错人或找不到人 | 保存 contact_key，提交前从最新通讯录重新解析目标 |
| 各模块绕过统一意图入口发送 | 同一个人同时收到 AI、定时、关键词时仍会乱序 | 所有真实发送进入 owner，同会话意图链覆盖全部来源 |
| 关系扫描中途释放主窗口 | 其他任务切换主窗口后继续滚动会漏扫或误判完成 | 手动全量扫描不分片、不释放、不允许中途停止；失败后由用户从顶部重扫 |
| 扫描整体耗时超过 180 秒 | watchdog 把正常的几分钟扫描误判为卡死 | 每次成功读取或滚动后 heartbeat；单个底层 UI 调用卡住时仍触发恢复 |
| UI owner 被误当成 JSON 锁 | 本地写盘和微信动作耦合，文件慢也会堵消息 | 各数据域独立锁 + 原子替换；owner 只执行微信动作 |
| 新微信 UI 调用未登记 | 直接 UIA 点击、窗口组件或边缘 wxautox 调用绕过 owner | 静态边界测试；未知调用默认独占，实测后才能降级 |
| Web/状态线程读取 bot.wx.nickname | 看似只读仍跨 COM 对象线程，可能随机失败 | 启动时缓存纯字符串身份和状态快照，owner 外禁止访问 bot.wx |
| 管理员/接管 helper 继续接收 chat 对象 | 业务线程绕过 owner，或 monkey-patch COM 对象方法 | helper 只返回纯数据意图；删除 chat.SendMsg 包装和改写 |
| owner 调用永久不返回 | 唯一进程内 UI 通道停止 | 最小监控线程按截止线记录栈并退出整个面板进程，由启动脚本限次恢复 |
| 连续相同短句 | 一条本地记录误吞多个可见气泡，漏掉第二条合法消息 | 按出现次数逐条抵消，每条本地记录最多匹配一个气泡 |
| 没有上下文锚点 | 旧尾部已经超出可见范围，停机对话无法从旧锚点续接 | 把过滤后的当前可见快照作为新的历史尾部，按时间分隔和窗口顺序补入本地缺失项 |
| `StopListening()` 永久不返回 | 停止按钮和面板请求一起卡住 | HTTP 立即返回，后台停止受截止线保护 |
| 面板同步等待备注/扫描/好友申请 | 浏览器请求因排队或 UI 慢而超时 | 请求只提交并返回状态，继续复用模块进度轮询 |
| 删除 CLI 后全量关系扫描占用主窗口 | 扫描期间聊天 UI 排队 | 这是手动操作的明确代价；连续扫到底保证结果完整，面板显示运行进度 |
| 删除随机点赞 | 账号少一种自动活跃行为 | 明确接受该损失，换取更少主窗口冲突和误操作 |

这套方案有意不利用聊天子窗口并发。通讯录子进程运行时 UI owner 不操作微信，其他时候也只有 owner 一次调用。这是基于正确性和维护成本的保守选择，不是否认微信具备多通道能力。

## 十三、最终验收标准

以下项目全部通过，才算重构完成：

1. 全量现有单元测试通过，并新增单 UI owner、非抢占排队、意图替换、语音、补洞、停止和重启测试。
2. 通讯录自动维护固定每批 50 人，连续至少 3 批能在 300 秒内完整返回，成功字段与改造前逐项一致；失败、超时和用户停止不污染正式档案。若实机不能满足，先查内核/环境，不能静默缩成其他批量或假装维护成功。
3. 通讯录父进程启动子进程后进入全屏障；50 人维护期间 owner 不执行任何后到微信意图，消息业务线程不调用 AI，文字、图片、语音、文件和转发全部按原顺序等待且不终止通讯录。
4. 通讯录完成/超时后先恢复聊天页，再处理最早独占任务；存在独占等待时下一批维护不能插队。
5. `GetNextNewMessage/GetListenMessage` 在未完成专项实测前不与通讯录并行；期间始终最多一个 poll-due，恢复后能补回全局新会话发现。
6. 私聊和启用语音识别的群聊：新语音有正文时零额外重读；只有时长时约 5 秒和约 10 秒各最多一次普通窗口重读，同会话多条语音共用快照。
7. 人工 self 消息、连续相同短句和相同图片按实际次数补入；有锚点时补齐整个可见窗口，无锚点时把当前可见快照作为新尾部；当前触发消息不得重复。
8. UI owner 外对 `bot.wx`、Chat、NewFriend、Moments、SessionBox、UIA 或窗口组件的访问会被边界测试拒绝；唯一的 Message 例外是实时图片 / 引用在原回调线程取得 owner FIFO 时段后下载，且对象不离开回调栈。状态页只读纯数据快照。
9. 私聊、群聊、全局监听、图片/引用、AI/关键词/轮数结束语、群欢迎、语音、拆分回复、自定义转发、接管、素材/AI 自动转发、定时/随机消息、朋友圈、通讯录、关系扫描、新好友和主动申请逐项回归通过。
10. 同一会话同时触发 AI、关键词、管理员提示、定时/随机文字、文件和新好友欢迎时，所有真实发送按唯一意图链排序；只有尚未开始的过时 AI 意图可替换。
11. 轻发送发现子窗口失效后按“AddListen -> 重新定位 -> 原发送”执行，后到同会话动作不能超车，也不会发到错误窗口。
12. 实时图片 / 引用在 owner FIFO 授权时段内使用原回调对象下载；任何已开始的微信任务结束前都不得下载，不事后猜测，也不按媒体类型抢占。主动 quote 和素材转发在 owner 内重新定位，歧义时拒绝执行，相同内容连续出现时不会猜错对象。
13. 排队后删除/停止任务、热更新配置或修改好友备注，owner 调用前能取消旧意图或通过 contact_key 重解析，不向历史名称发送。
14. 在每类任务的调用前、调用中、调用成功但尚未写记录三个位置注入进程退出，结果分别收敛为 pending、uncertain/核验、done，不整批重跑。
15. 在 AI 生成中注入进程退出，重启后能依据未答入站游标合并缺口重新生成一次；人工 self 后不会再补发机器人回复。
16. 语音、文件、quote、素材转发和好友申请在“实际可能成功但调用未返回”时不盲目重发；结果明确为成功或 uncertain。
17. 朋友圈已经发布但状态未落盘时不会重复发圈；备注/标签达到目标值后重试会直接收敛为成功。
18. 手动关系全量扫描从顶部连续执行到自然末尾，中间不插入其他微信 UI；命中 1000 次保险上限时标记 `partial`，正常数分钟运行不触发 watchdog。
19. 新好友检测后的原 NewFriend 对象即使失效，接受事务也会重新读取并唯一定位；重名或信息不足时不猜测接受。
20. 面板触发备注修复、关系扫描和好友申请时 1 秒内返回排队/运行状态，不让 HTTP 请求等待真实微信动作。
21. 人为注入轻操作卡死、独占操作卡死和通讯录卡死时，分别按 30 / 180 / 300 秒边界恢复；停止接口同样在 1 秒内返回。
22. 至少 2 小时生产形态压力测试覆盖高频入站、通讯录全屏障与恢复后积压处理、语音输入/输出、图片、素材转发、关系扫描和人工介入；无漏回复、重复回复、孤儿子进程和错误窗口。
23. 本地任务、记忆、通讯录和关系状态继续使用各自域锁与原子替换；owner 卡死或进程恢复时无 JSON 丢更新。
24. 生产代码中不存在第二个通用 UI worker、加权容量门、client generation、`_WechatActionLockedChat` 或 `_chat_send_locks`；复杂度删减可由静态检查验证。
25. 通讯录真实运行期间分别收到固定监听私聊、群聊、图片和语音；普通回调只复制纯数据入队，图片 / 引用回调只能等待 owner 授权，批次恢复前不下载、不开始业务处理或其他微信操作，恢复后按原到达顺序继续且不丢失原消息描述。
26. 原样 `打开软件.bat` 能加载最终代码并保持单面板、单机器人 runtime；本任务启动的临时实例均登记启动器、服务 PID 和端口，测试结束后不遗留额外进程或监听端口。已经启动机器人的实例必须先正常停止，不能用强杀掩盖监听残留。

## 十四、不做的事情

- 不引入动态并发、自适应调参或通用任务编排框架。
- 不增加第二个通用 UI worker、加权容量门、client generation 或多级优先队列。
- 不把整个机器人再包进新的 UI 子进程/IPC 框架；只有通讯录保留已经验证过的最小子进程。
- 不增加三档、五档之类的 UI 性能配置。
- 不把 `hash` 升级成全局消息主键，也不为单账号队列拼接账号维度组合键。
- 不用新的 CLI 或数据库读取工具替代 `wechat-cli`。
- 不给上下文补洞增加单窗口手动修复入口。
- 不为了旧配置保留长期兼容层；这是个人 fork，可以在实施时一次性清洗旧配置。
