# WXBot Pro 开发指南

这份文档面向本地维护者和后续 AI Agent：只记录“代码现在怎么跑、哪些边界不能乱动、改完怎么验证”。面板操作请看 `docs/WXBot Pro 使用说明.md`。

本项目的最高目标是：保证回复对象和内容正确、聊天记录 / 会话记忆可信、通讯录维护与各类营销任务完整执行，以及微信 UI 卡住后能够自动恢复。几分钟回复延迟是可接受的代价；错回复、错图片、重复发送、任务被打断和记录污染不可接受。

## 维护原则

- 本项目是个人自用 fork，优先当前实际体验和代码可维护性，不为旧任务、旧实例、旧记录额外保留兼容层。
- 能收敛成单一真源时，不并行维护两套字段或流程。
- 不提交本地私密配置和账号数据，尤其是 `data/config/`、`data/accounts/`；`data/prompt/` 下只有 `模板.md` 和 `模板-人设近况.md` 纳入版本控制，其余人设和人设近况 Prompt 保持本机私有。
- 高风险链路改动优先补行为测试：登录、消息路由、图片、发送、会话记忆和任务调度。
- 模块拆分只整理本项目业务层，不顺手改 wxautox4、监听、下载或微信窗口控制底层。
- Windows PowerShell 看到中文乱码时，先按终端显示问题处理，不直接重写中文内容。

## 代码结构

- `打开软件.bat`：启动入口。优先用 `runtime/python/` 的 Python 3.12 创建或复用 `venv/`，安装依赖后运行 `web_server.py`；`runtime/python/` 是发布包携带的基础运行时，`venv/` 是本机可重建的依赖环境。
- `web_server.py`：Flask 面板和管理 API，负责登录、配置读写、接口测试、备份、页面 API，以及启动 / 停止机器人。
- `templates/dashboard.html`：面板主体。
- `wxbot_core.py`：机器人运行时总编排，负责监听业务、AI 回复、统一任务扫描和向 UI owner 提交纯数据意图。
- `core/wechat_ui_runtime.py`：唯一持有 wxautox4 对象的 owner 适配层，负责真实微信读取、发送和窗口操作。
- `core/`：底座能力，例如配置、Prompt、媒体、记忆、发送、通讯录身份校准和调度。
- `feature/`：业务规则，例如监听维护、素材转发、定时任务。
- `extension/`：外部增强，例如邮件通知、WXBot Pro 远程访问。
- `tools/`：本地复现脚本、备份脚本和专项测试辅助，只放临时、测试性质工具。
- `tests/`：行为保护测试。

## 运行链路

### 启动层

```text
打开软件.bat
-> 创建 / 复用 venv
-> 安装脚本内置依赖清单
-> 运行 web_server.py
-> 面板优先开放在 http://127.0.0.1:10001（被占用时顺延）
```

`打开软件.bat` 自己维护 Python 依赖清单，不读取外部 `requirements.txt`。它会兜底安装 `Pillow`，并在系统缺少 `ffmpeg` / `ffprobe` 时下载到 `venv/tools/ffmpeg/`。

生产环境不安装、不初始化、不检测也不读取 `wechat-cli`。通讯录、上下文补洞和关系扫描都走已登记的微信 UI owner 路径；不要恢复本地数据库旁路。

### 面板层

`web_server.py` 负责：

- 登录态、session、首页和日志拉取。
- `config.json`、`admin.json`、`email.json` 等配置读写。
- 接口连通性测试和视觉能力测试，并按稳定 API ID 写入 `api_capability_map`；接口列表序号只能用于展示，不能作为任何保存引用。
- Prompt、人设近况、会话记忆、聊天记录、通讯录、素材转发、备份等页面 API。
- 统一任务工作台 API：`/api/task-workbench/<module>` 与 `/api/task-workbench/<module>/runtime`。
- 素材池管理 API：`DELETE /material_outreach/materials` 只清空当前所选微信号的 `materials.json` 和同账号运行时素材句柄，不删除任务配置、运行队列或历史转发记录。
- 启动 / 停止机器人：`/start_bot` 后台创建 `WXBot` 并调用 `run()`；`/get_startup_status` 轮询真实启动结果；`/stop_bot` 立即返回 `stopping`，owner 先拒绝新意图并取消未开始队列，当前动作结束后由机器人线程执行 `StopListening()` 收尾。
- UI 卡死恢复：owner 等待 wxautox4 全局锁时不启动 watchdog，也不写 `inflight`；只有真正进入微信处理器后才开始动作截止线。轻操作为 30 秒后再留 10 秒收敛，独占操作为 180 秒，通讯录采集为 300 秒。运行中卡死退出码 `86` 会由启动脚本自动恢复，用户停止阶段的 `87` 只恢复面板、不启动机器人；30 分钟内最多自动恢复 3 次。

### 机器人层

`WXBot.__init__()` 初始化配置、聊天接口主备状态、回复轮数存储、Prompt 系统、素材转发和消息合并状态；微信 UI owner 在监听初始化时创建。

真正接入微信发生在 `init_wx_listeners()`：启动 UI owner，由 `WeChatUIRuntime` 在 owner 线程创建 `WeChat`、读取当前 `wx_id` 并启动监听器。普通私聊总开关开启且范围为 `仅白名单` 时注册白名单固定窗口；范围为 `全部好友（除黑名单）` 时先启动全局扫描泵，首次空扫描后才放行固定群聊和素材来源建窗。私聊总开关关闭时不登记白名单、不启动全局扫描，但群聊和素材来源仍按各自配置登记。业务层只接收纯身份和消息快照。

素材来源不在配置中保存私聊 / 群聊类型：建窗时必须让微信按名称返回实际窗口，再把发现的内部 `ConversationRef` 缓存到运行期；不得把素材来源默认成私聊，也不得要求用户重复配置普通监听名单。

`WXBot.main()` 每轮负责微信在线 / 窗口状态检测、新好友检测、窗口恢复与清理、运行中任务热更新、统一时间任务扫描、AI 自动转发待发送队列、通讯录自动维护检查。AI 自动转发主开关关闭时，AI 待发送队列和文案预生成队列中的未执行记录都会清理，不能继续进入微信发送。全局未读扫描由独立扫描泵负责，不再由主循环同步调用一次。

时间任务统一由 `core/scheduled_tasks.py` + `wxbot_core.py` 主循环扫描，不再依赖多套 `schedule.run_pending()`。

## 消息处理链路

先看 [消息处理流程图](消息处理流程图.html) 建立全局概念；这里保留代码入口、状态边界和实现约束。涉及监听补窗、UI owner 或通讯录独占时，同时看 [监听维护流程图](监听维护流程图.html)。两张图均为离线 HTML，浏览器直接打开即可查看，并会在窄屏下按步骤纵向展开。

```text
微信监听回调 / 全局扫描泵
-> 转成纯数据快照；扫描批次一次性写入 SQLite 消息事实
-> 按需下载媒体或用新窗口快照补读语音正文
-> 扫描落库成功后登记按需建窗
-> message_routing 第一轮入口分流
-> 素材来源投喂 / 关键词回复 / AI 回复
-> 普通消息处理
-> 私聊好友消息进入连续消息合并队列
-> AI 回复前按需补齐最近上下文，再读取 history 组装 Prompt
-> 回复预处理（清洗、准入、必要时重写 / 兜底）
-> 拆分多条、后续气泡间隔
-> 向唯一 UI owner 提交 SendMsg / SendFiles / forward 等纯数据意图
-> 成功发送后写入输出记录
-> 按需更新会话记忆
```

实时观察只有 native ID 相同时才做强去重；hash 或正文相同不能删除两次真实消息。项目内部会话类型固定为 `private / group`，wxautox 的 `friend` 只在 `ConversationRef` 入口转换。业务线程只传递纯数据，会话对象和原始消息不跨线程。

所有已经开始的微信动作不可抢占；owner 尚未取得全局锁时，只有持锁 callback 的释放可以先完成。普通任务失败只结束或延后当前任务；`AddListenChat` resize 的精确 `1400 + MoveWindow` 首先只做监听局部恢复和监听重建，只有重建后两个不同会话在 10 分钟内连续耗尽同类恢复才升级重绑。其他 Windows `1400` 或 COM/RPC 断开等客户端级证据仍可直接重绑。通讯录采集是唯一跨进程例外，期间暂停监听并保持全屏障，完成或超时后恢复聊天页和监听。

发送回声、投递状态、联系人资料和静默失败日志等细节见后面的“关键行为边界”和数据真源小节，避免在消息总览中维护第二份规则。

## 运行中同步

面板交互使用 `templates/static/jquery-3.6.0.min.js` 本地资源。不要改回外部 CDN 单点依赖，否则网络不可用时页面仍能显示但启动、停止和保存按钮不会绑定事件。

`/save_config` 在机器人运行中做两类同步：

- API 相关字段变更时，调用 `apply_runtime_api_config_update()`，刷新聊天接口实例，并把聊天主备状态重置回主接口。
- 定时消息、素材转发等任务配置变更时，调用 `request_runtime_task_reload()`，由主循环在安全时机重新载入后续任务表。

已经开始执行的一轮不会被强行打断；这不是热重启整个机器人。

## Prompt 规则

- 普通私聊回复、群聊回复、图片最终回复、素材转发判定、素材附加文案，优先走 `PromptSystem`。
- 辅助视觉分析、结构化视觉笔记、会话记忆提取 / 修复这类固定协议型 Prompt 独立维护。
- 不要在 `wxbot_core.py` 或 `web_server.py` 里平行拼 `base_prompt / persona_status_block`。
- 当前聊天轮次固定把软件处理时间放进 `[运行信息]`；可选的 `消息时间` 只在 `[用户消息]` 下、整批正文前出现一次，不给每个气泡重复加标签。
- `消息时间` 在 `WeChatUIRuntime.poll_messages()` 的全局新消息入站边界确定。优先取当前返回批次中、最后一条真实入站消息之前最近的 `TimeMessage.time`；批次没有可用时间条时，从该消息的原始控件向前检查最多 30 个同级控件，只对 `ClassName == 'mmui::ChatItemView'` 且 `AutomationId` 为空的候选调用 wxautox4 `parse_msg`，最终必须确认 `type == 'time'`。
- 解析出的完整时间只写入当前批次最后一条真实入站 `MessageEnvelope.time`，随后落为该事件的 `native_time`。AI 只读取当前轮事件 ID 中最后事件自己的 `native_time`，不搜索、继承补洞或历史记录中的时间条，也不读取当前消息之后的时间条。
- 没有可用时间条、原始控件缺失或控件 / 解析 / 存储查询异常时都按“无消息时间”继续，不得中断正常 AI 回复；禁止用处理、接收、入库或扫描时间代替消息时间，也禁止为此调用 `GetAllMessage()`。

## 模块边界

落位原则：

- 去掉“这是微信机器人”前提后仍成立的能力，优先放 `core/`。
- 明显依赖当前业务规则和流程判断的能力，优先放 `feature/`。
- 面向外部系统的接入和增强，放 `extension/`。

仍应留在 `wxbot_core.py`：

- 监听业务注册、主循环和业务线程编排。
- 聊天主备切换、AI / TTS / Prompt、消息合并、任务扫描、主循环健康检查和运行中热更新入口。
- 纯数据 UI 意图的生成与发送结果回写；不得缓存或直接调用 wxautox4 对象。

`core/wechat_ui_runtime.py` 保留 `WeChat` 创建、窗口定位、真实 `SendMsg / SendFiles / SendAudio / forward / quote / new.accept` 和联系人资料等 owner 内动作。

## 数据真源

- `data/config/config.json`：主配置。
- `data/config/admin.json`：面板账号密码。
- `data/config/email.json`：邮件通知配置。
- `data/config/reply_count.json`：私聊好友与群聊成员的回复次数限制计数；群聊键由群名和发言人共同组成。
- `data/config/runtime_metrics_v1.json`：状态面板和数据图表使用的小时级运行统计。文件存在但读取失败时必须保留原文件并拒绝写入，不能重建为空统计；机器人每次启动只记录一次存储错误，恢复写入后才允许再次记录。
- `data/prompt/`：人格模板和人格近况文件。
- `data/system_prompts/`：系统 Prompt 片段及其备份。
- `data/accounts/<wx_id>/message_store.sqlite3`：消息事实、聊天记录、会话版本、回复任务、逐气泡投递状态和非幂等 UI 提交围栏的唯一真源。旧版 `memory/*_memory.json` 不再由生产代码读取；已有本地数据使用 `tools/migrate_legacy_message_history.py` 一次性迁入，验证后移除旧目录，不保留长期双读兼容层。
- 聊天记录保留上限按会话物理删除超量 `chat_events`，并只在移除关联事件后保留投递状态及 `uncertain` 状态；活跃回复任务关联的事件不得删除，禁止因为记录清理而重发。
- `data/accounts/<wx_id>/chat_memory/`：会话记忆 JSON 真源。
- `data/accounts/<wx_id>/contact_profiles/contacts.json`：通讯录档案真源，使用 v2 瘦身结构。
- `data/accounts/<wx_id>/contact_merge_backups/`：联系人合并前的账号级保险备份。
- `data/accounts/<wx_id>/tasks/`：关键词、定时消息和素材转发等任务模块。
- `data/accounts/<wx_id>/relationship_scan/relationships.json`：关系扫描结果。
- `data/accounts/<wx_id>/friend_request/state.json`：好友申请设置、候选人和执行记录。
- `data/accounts/<wx_id>/config/voice_reply_state.json`：语音回复运行态。
- `data/accounts/default/`：只有没有运行中微信号、没有 `last_wx_id`、也没有历史账号数据时才使用。
- `wxbot_save/`：微信下载原件和 AI 图片压缩副本缓存，不是长期数据真源。
- `wxbot_logs/`：面板运行日志。
- `backups/data_时间戳/`：面板一键备份产物。

通讯录 v2 只落盘联系人真源字段：`contact_key`、`wechat_id`、`wxid`、`nickname`、`remark`、`region`、`source`、`added_at`、`signature`、`tags`、`status`、`warnings` 和维护状态字段。不要把 `display_name`、`send_name`、`send_target`、`name` 当作联系人档案字段写进 `contacts.json`。

通讯录名称分三层：

- 档案层：只保存微信资料和本地维护事实。
- 接口 / 调用层：通过 `core.contact_profiles.contact_public_view()`、`contact_send_target()`、`contact_display_label()` 从档案层临时派生 `name` / `send_target`。
- 运行记录层：素材转发、定时任务、AI 前言队列等历史证据可以保存当时的 `send_name` / `display_name`，但这些字段不能反向污染通讯录档案。

如果传入对象同时包含事实字段和临时字段，通讯录派生函数必须优先使用事实字段。保存入口 `save_directory()` 会再次归一化，防止展示名、发送目标等临时字段回流。

## 关键行为边界

### 面板账号边界

页面选择的 `wx_id` 只决定历史数据的查看、编辑和清理范围；任何会真实操作微信的面板入口都必须通过 `_require_running_bot_action()` 同时取得当前机器人实例和已绑定的 `bot.wx_id`。请求携带的 `wx_id` 不得作为真实动作的账号真源；机器人线程存在但 `bot.wx_id` 尚未绑定时直接提示稍候，不能回退到页面账号。

通讯录立即建档只有在请求账号与运行账号相同时才接受页面的 `start_name`，账号变化时必须丢弃旧游标并从通讯录顶部开始。好友申请“执行一次”在同一请求中先把当前表单设置保存到运行账号，再排队执行；保存失败不得继续提交。`/get_status` 通过 `running_wx_id` 暴露运行账号，前端只在该值发生变化时同步一次通讯录、关系扫描和好友申请视图，不得在每轮状态轮询时强制覆盖用户后续选择的历史账号。

### 微信 UI owner

项目主动发起的全部真实微信动作只由一个 UI owner 线程执行，包括监听、私聊 / 群聊回复、文件和语音、quote、素材转发、定时消息、备注 / 标签、关系扫描、新好友和好友申请。关系扫描的微信标签自动同步只有在自动扫描总开关和“同步到微信标签”同时开启时才允许领取队列；总开关关闭会暂停待同步队列，保留记录供重新开启后继续，不撤销已写入微信的标签。wxautox4 自己创建的监听 callback 线程是中间件边界：原 callback 绑定的 `Message` 下载仍在原线程执行，但必须先取得 owner 预约，并继续受 wxautox4 全局 UI 锁串行保护；这不允许项目再创建第二个 UI 执行线程。业务线程只提交纯数据意图；wxautox `Chat`、`Message`、`NewFriend` 和 UIA 对象不得跨线程缓存。联系人高层入口在缺少 owner 时直接失败，好友申请 UIA 适配器还必须收到 owner 线程断言，不能依赖调用者自觉。

监听器或桌面对象失效时也不能在业务线程重新创建 `WeChat`。监听运行时重建提交原子 `REBUILD_LISTENER` 意图；需要重新创建微信客户端时才提交独占 `REBIND` 意图。两者都由 `WeChatUIRuntime` 在 owner 线程完成，生产边界测试只允许 owner runtime 和通讯录最小 worker 构造 `WeChat`。实机已验证客户端重绑前后微信身份一致、固定监听恢复且子窗口可继续读取。

`core/wechat_recovery.py` 是微信 UI 自恢复的唯一决策模块：`UIWatchdog` 只检测已经开始的 owner 动作是否越过截止线，`WeChatRecoveryCoordinator` 集中保存等待、观察、重建、重绑和重启状态，并生成统一日志与面板快照。监听异常和看门狗超时只向协调器报告事件；协调器决定恢复层级，但重建 / 重绑仍通过 owner 意图执行，进程退出后仍由 `打开软件.bat` 按恢复预算重新拉起，任何恢复代码都不得从看门狗线程直接访问 wxautox 对象。

owner 对普通任务按 FIFO 执行，整个 handler 都处于同一段 wxautox4 全局锁事务中；发送动作组、素材读取 / 转发、关系扫描、资料修改、新好友等多步骤任务一旦开始，callback 和其他任务都不能插入中间。只有“持锁 callback 释放”可以在普通任务尚未取得 UI 锁时先完成，普通任务随后回到原队首且只执行一次。AI 拆分气泡、quote 后续文字、关键词多项、新好友欢迎和定时消息都逐项提交；每一项开始前复核会话或任务版本，回复意图还要复核 60 分钟 `expires_at`，让新消息、人工 `self`、过期或配置变化取消尚未开始的剩余项。停止时，尚未进入微信处理器的已领取回复动作退回 `pending`，不写成取消；下一次启动只要仍在 60 分钟内就可恢复。已经进入微信处理器的动作结果不明时仍必须标为 `uncertain`，禁止自动重发。通讯录最小采集子进程是唯一跨进程并发例外，其父进程在采集期间暂停后台监听并保持全屏障。调用方不设置固定排队等待秒数，必须等待意图完成、主动停止或版本校验取消；等待 wxautox4 UI 锁最多 30 秒且没有 watchdog 截止线，失败时微信处理器尚未调用。取得锁后，轻操作的进程级卡死边界为 40 秒（30 秒动作截止线和 10 秒异常处理窗口），独占操作 180 秒和通讯录 300 秒是当前动作自身的卡死边界，不能拿来充当队列等待上限，否则会产生调用方已报失败但微信稍后仍执行的晚到操作。

非幂等恢复必须区分调用前、调用中和成功落盘后。文件、语音、quote、转发和动作组由 `MessageStore` 的 `ui_deliveries` 表冻结；定时、素材、好友申请和资料修改继续使用各自真源。进程退出场景要用真实退出测试覆盖，不能只捕获普通异常。

### 全局扫描与动态监听

私聊总开关开启且范围为 `全部好友（除黑名单）` 时只有一个全局扫描泵，任意时刻最多一个 `mode=next` 的 `POLL_MESSAGES` 在排队或执行。wxautox 返回 `official` 等非 `private / group` 会话的真实消息时，必须在 UI 原始结果进入 `ConversationRef` 前明确跳过，不落库、不建窗，并按无新增事实退避；不得因此停止扫描泵。`GetNextNewMessage` 的 `msg` 和 callback 捕获均为空时，一律返回正常空批次，即使 wxautox 此时把 `client.chat_type` 留为 `None`；空批次不带“不支持会话”标记、不写日志，并进入 3 秒低频。每个非空业务扫描批次在 owner 外通过 `InboundCoordinator.accept_batch()` 和一个 SQLite 事务保存后立刻进入业务队列；不等待其他会话先被读取。启动积压未读尚未清空前不得申请动态监听窗口，首次空扫描后才恢复按需建窗；稳定运行后的新消息仍可登记建窗。重复结果没有新增事实时指数退避到最多 5 秒。SQLite 提交失败必须 fail-stop，不能继续把微信未读标成已读。

扫描前通过同一 owner 动作读取轻量未读快照。真实好友消息少于快照未读数、扫描耗时达到 wxautox4 的 10 秒上限，或返回达到 30 条上限时，保留会话级覆盖诊断并写入本地 `DEBUG` 日志；已取得事实继续回复，首页仍显示正常运行。只有扫描 fail-stop 才进入用户可见的红色异常状态并让 `/runtime_health` 返回不健康。第一阶段禁止自动 `deep`，也不修改 wxautox4 内置上限。

动态监听采用按需补窗。普通增删监听不触发微信客户端重绑，不恢复主循环高频巡检。普通补窗失败先按 30s / 60s 延后，之后按 60s 继续尝试；持续 600s 仍不可用时标记降级并改为每 300s 低频恢复。`ListenerWindowSupervisor` 只保存会话名、重试时间和错误，不持有消息；消息在尝试补窗前已经进入 SQLite 事实库。同一会话只保留一项窗口恢复任务。黑名单模式重建监听器后重新扫描到空，再由 supervisor 补窗；只有“已监听但无子窗口”残留状态允许受控关闭重建。

监听是否就绪只由 runtime 判断：必须同时存在有效物理 HWND，并且 `client.listen[name]` 已登记匹配的 `(Chat, callback)`。当前运行期缓存只有满足这两个条件才能复用；`StopListening` 必须使缓存失效。`GetSubWindow()` / `GetAllSubWindow()` 仍保留为 runtime 内部发现接口，但“找到子窗口”本身不能证明 callback 已登记。业务层补窗和初始化校验使用 runtime 的严格 `AddListenChat` 结果；固定监听巡检则在 owner 内一次读取同样严格的登记快照，只对缺失登记补窗，不再给健康会话重复提交 `AddListenChat`。严格校验确认原登记本来有效时，不得报告窗口恢复或重复触发上下文补洞；删除监听时，即使物理窗口已经消失，也必须调用内核 `RemoveListenChat()` 清除残留登记。

`AddListenChat` 若只在首次调整窗口大小时报出 Windows `1400 + MoveWindow`，说明子窗口可能已经创建，但 resize 使用了瞬间失效的旧句柄，callback 也未必完成登记。runtime 先用 `GetAllSubWindow()` 按名称和 `private / group` 找回有效窗口，首次未找到时等待 150ms 再查一次；找到后重新 `auto_resize()`。若 callback 已正确登记则直接复用，否则最多再调用一次 `AddListenChat` 完成登记或补建，最后仍按“有效 HWND + 匹配 callback”验收。当前内核明确失败的 `WxResponse` 必须立即拒绝。该局部恢复只把精确的 `1400 + MoveWindow` 收敛为“监听子窗口未准备好”；其他 Windows 1400、COM / RPC 和普通控件异常原样上抛给既有恢复策略。单次局部失败不得关闭 `resize` 或直接重绑整个微信客户端，只有下一段定义的连续复发规则可以升级。

精确 `MoveWindow 1400` 的局部恢复最终失败后，先只提交一次 single-flight 的监听运行时重建。该重建是 owner 内的一个原子意图：`StopListening`、清 runtime 登记、`StartListening` 与固定监听恢复之间不得插入普通任务；当前已验证版本中，`StopListening()` 会关闭已打开的监听子窗口，因此重建前不得额外逐窗关闭，停止后的旧窗口清理请求可安全空操作。全局扫描模式只重启监听和扫描泵，不同步创建全部动态窗口，且不得清空动态窗口记录：首次扫空后仍要由 `ListenerWindowSupervisor` 按这些记录提交延后补窗。重建成功后进入 10 分钟观察：两个不同 `(chat_type, ConversationRef)` 的同类最终失败只有在首个失败后的 10 分钟内连续发生，且中间没有成功的真实子窗口读取、严格登记或发送，才升级为客户端重绑；重绑完成后清空计数并进入下一观察期。重绑后的观察期再次达到同一阈值，机器人以退出码 `86` 交给现有启动器受控恢复，仍受 30 分钟最多 3 次预算限制。重建或重绑成功即开始稳定计时，连续 10 分钟未再形成失败序列时回到正常级别。普通 `ListenSubwindowNotReady` 永不计数；主客户端 Windows `1400` 或 COM/RPC 断开仍可直接走既有重绑路径。

局部找回成功使用 `自恢复【局部找回】成功`，只表示已找回并校验刚创建的监听窗口，不属于升级。三层恢复日志仍统一使用 `自恢复【监听窗口重建】`、`自恢复【微信客户端重绑】`、`自恢复【机器人重启】` 标签，并明确标记开始、等待、执行、成功或失败。排查时按标签搜索即可还原升级路径；不要使用笼统的“监听器自动恢复”掩盖实际执行层级。

自动恢复成功日志先写从发现异常到恢复可用的总耗时，再在括号内列出等待恢复处理、客户端探活（或探活及重绑）和监听重置耗时。全局扫描模式只在自动恢复后首次扫空时追加 `自恢复【全局扫描】阶段耗时`，记录扫空耗时与已提交的按需补窗数量；每个实际补窗仍复用微信 UI 耗时日志。该记录只用于定位耗时，不改变动态记录、补窗队列或恢复升级规则。

固定监听每 60 秒低频巡检一次，但不能和全局监听延后补窗抢微信 UI。UI owner 正在执行或排队、以及监听恢复进行中时，本轮固定巡检直接延后；不取消任务、不改变 owner 的 FIFO 和恢复插队规则。

### 上下文补洞

保存聊天历史且对应的 `chat_context_repair_switch` / `group_context_repair_switch` 开启时，只有监听窗口从不可信或不存在变为当前 runtime 可信可用，才按会话创建或推进 `generation` 补洞标记；没有标记时不读取 `GetAllMessage()`。补洞领取当前代次，成功后直接删除同代标记；执行期间窗口再次恢复产生新代次时，旧成功不得清除新标记。失败后固定退避再试，不周期巡检，也不滚动深历史。两个开关分别控制私聊 / 群聊 UI 补洞，`memory_context_switch` 只控制 history 是否带入 AI。

补洞只修复当前可见的尾部断层。当前触发消息边界必须唯一确认：优先 native ID，其次唯一 `hash_text`，最后才使用唯一的规范化气泡序列；无法确认时整批跳过并退避。临时合并的连续私聊必须用原始来源气泡定位并排除本轮已经落库的全部事件，合并对象本身不写 history；微信原生 `type=merge` 是单个气泡，只保存 wxautox 暴露的外层预览。截断当前批次后，只在最近本地尾部查找唯一连续重合：单条 native ID 可作为强重合，正文重合至少连续两条；找到后整段补入其后的可见气泡，找不到则把全部可见尾段作为最新记录补入。模块不修复历史中间的零散缺口，不做内容级时间窗去重、加权对齐、OCR 或特殊消息展开；重复短句、图片和语音按气泡次数保留。

`TimeMessage` 不作为普通消息事实，也不参与身份和去重；补洞时可将其原生显示时间继承给补入的历史气泡，但当前 AI 轮次的消息时间不从补洞结果或历史记录获取。没有原生时间的补洞事件按窗口顺序放在当前批次之前，内部排序时间不对面板和模型显示。最近历史、删除边界、尾部计划和批量写入必须在同一个 `BEGIN IMMEDIATE` 事务中完成；无历史重合且清空记录后尚未形成新历史时不得补回旧气泡。补洞使用当前事件 ID 与窗口序号生成稳定批次身份，不推进会话版本、不创建回复任务；本次写入的消息由补洞结果直接追加到本轮原始 history，再统一执行模型可见过滤和条数裁剪，不能等到下一轮才生效。

机器人运行且监听正常时，人工 `self` 消息先写 SQLite，再推进会话版本并取消尚未发送的旧回复，不依赖补洞。机器人 outbound echo 也写入同一条已确认发送事实，但不推进版本。每个 UI 观察只允许一个事实写入入口；没有 native ID 的两条同文消息必须保留，不能退回内容级短时去重。

### 通讯录与身份

通讯录自动维护和手动建档的完整资料采集必须走 `feature/contact_auto_collector_worker.py` 最小子进程。主进程负责 owner 调度、300s 硬超时、PID 级 kill / `taskkill /T /F` 兜底和 `SwitchToChat` 恢复；不要把 `GetFriendDetails` 搬回主进程。每批 50 人、完整轮 7 天固定为内部参数。

worker 每批必须按 `SwitchToContact -> 聚焦通讯录列表 -> Home -> 验证顶部固定入口“新的朋友” -> GetFriendDetails(50)` 执行；只发送 Home 而不验证回顶不算成功。当前 wxautox4 `GetFriendDetails` 的 callback 实机语义与 `.pyi` 注释相反：返回 `False` 会继续寻找，第一次返回 `True` 会停止 callback，并从命中项开始读取，命中项包含在返回结果且计入 `n`。

callback 中的名称只用于精确定位，不能把同名出现次数当身份。worker 必须用微信号 / wxid，缺失时用完整资料指纹复核首项身份，并按同一稳定身份去除虚拟列表重复行。下一批游标只能从批次尾部选择“此前未出现同名、且本批同名只对应一个稳定身份”的安全项；没有安全游标或身份不一致时整批失败，不猜测位置。主游标失败后持久化切换备用游标，备用游标也失败则从顶部重开。正常 50 人批次短批后，下一轮固定执行 `n=2` 尾部探针；只有原始结果至少 2 行、全部 identity 等于请求锚点且没有第二身份时才确认完整轮结束。单行、异常或 300 秒超时保留原游标和 `tail_confirm_pending`，不能写 `last_full_scan_completed_at`。游标和身份锚点只属于维护状态，不得写进联系人真源字段。

自动维护只有在最近一次全局扫描为空且没有 fail-stop、没有入站队列 / 待回复 / 建窗恢复 / 正在执行的 `tail` 补洞、owner 空闲且持续安静后才允许开始。历史覆盖诊断不阻止维护。仅等待下一条消息触发的 dormant 补洞代次不单独阻塞维护，否则无新消息的固定窗口会让通讯录永久饥饿。维护状态 `running` 只能阻止近期仍活跃的批次；超过维护间隔且至少 10 分钟没有活动时必须重新到期，避免进程重启后的旧状态永久卡住自动维护。

身份校准跟随通讯录维护、手动建档和备注修复成功触发，不在每条消息热路径刷新通讯录或扫描目录。聊天记录、会话记忆、关系扫描、任务引用和回复计数的改名 / 合并都通过账号级联系人合并链路处理，合并前写入 `contact_merge_backups/`。

身份判定不做模糊匹配，不维护历史别名：同 wxid、唯一备注、无备注时 `nickname + source + added_at` 唯一且只变 wxid 才自动合并，其余有意义冲突进入等待校准。

### 图片、语音与历史渲染

图片回复先生成结构化视觉笔记，再按最终回复接口是否支持视觉选择直接传图或视觉笔记转述。`image_parse.md` 只放图片处理规则，不塞具体图片解析结果。

AI 可见 history 统一走 `core/chat_history_format.py::build_model_visible_history(...)`。本地绝对路径不能喂给模型；图片使用 `[图片]` 加视觉笔记，语音只传转写正文，链接、小程序、视频、名片保留必要类型提示。

私聊图片进入连续消息合并队列，最多 `9` 张；成功处理后清理临时原图，失败残留最多保留 `10` 分钟用于重试。群聊图片本身只缓存到群级 pending visual context，后续文本触发 AI 且命中问图意图时才使用；缓存原图保留 `120` 分钟且首次成功回答后不清理，允许不同群友连续追问。上一批已经生成摘要，或新图片与上一张间隔超过 `120` 秒时，以新批次替换旧批次。进程重启后可从 SQLite 的近期群图片事实按需重建缓存，但只使用仍在有效期且本地文件存在的原图；原图缓存过期后只允许已持久化的视觉摘要随常规 history 降级，不承诺仍可读取原图细节。

子窗口实时图片 / 引用先把会话、方向、类型和占位正文写入 SQLite，再由 `core/wechat_ui_runtime.py` 在原 wxautox callback 线程调用原消息下载方法，并且必须先取得 owner 预约时段。callback 已持有内核全局锁时，owner 只可在自己的普通任务尚未取得锁、尚未开始时让它先释放锁；发送、转发、素材读取、关系扫描、资料修改、新好友、监听和通讯录等已经开始的动作都不可被抢占。全局扫描图片先随纯数据批次保存占位事实，再由现有业务媒体路径向 owner 重新定位下载。下载后只用本地路径标量补充原事件，原始 `Message` 不跨线程。

生产路径禁止调用 `msg.to_text()`，也不跨线程保留原始语音 `Message`。只有时长的私聊或已开启语音识别的群聊，先以原始入站事实落库，再在约 5 秒、10 秒各用普通 `GetAllMessage()` 读取一份新快照；按会话、方向、发送者、时长和 hash 匹配，存在多个候选时保持待处理，禁止按第一个候选猜测。得到正文时补充原事件，不新建第二条消息；`未播放`、仅时长、`voicemsg` XML 和失败状态不进入 AI / 模型 history，也不发送兜底提示，两次仍无正文则把原事件结束为 `not_required`。

### 发送、预处理与统计

AI 回复发送前统一走回复预处理：先按 `clean_ai_reply_switch` 清洗，再用 `evaluate_reply_preprocess_admission()` 做准入。不从脏输出里提取“最终回复”；不合格时只允许重写一次，重写仍不合格才走异常兜底或静默。

`api_error_reply`、回复预处理异常兜底和轮数超限固定回复的“只回复一次”状态都复用 `ReplyCountStore` 的回复循环窗口。新增同类提醒时，不另起重置时间或独立状态文件。

运行统计口径：`全部API调用` 统计机器人向 AI 大模型和正式 TTS 模型发出的真实请求；`聊天API调用` 统计为了回复当前聊天而发起的聊天模型请求，不包含素材判定、素材附加文案和面板测试 / 预览。

日志仍统一从 `core.logger.log()` 进入。Web 面板只展示用户可感知的四级运营日志：正常流程用 `INFO`，明确成功用 `SUCCESS`，局部失败但可继续运行用 `WARNING`，监听器、微信客户端、主线程或核心初始化受损用 `ERROR`；面板显示为“信息 / 成功 / 警告 / 错误”。`DEBUG` 只写入本地诊断文件，不进入面板，适用于运行实例 ID、内部路径、空补洞、拆分依据、接口索引和监听器逐步成功等正常技术过程。多行异常在面板只显示首行摘要，完整堆栈保留在文件。聊天 API 异常首行必须保留原始数字错误码，并用简短中文说明原因和重试 / 主备切换结果，SDK 异常类型、服务商响应体等技术详情放到后续行；同一 HTTP 状态码必须结合服务商 message 和异常类型判断，不能直接硬编码为单一原因。接口测试发现模型不支持图片属于能力结果，用 `INFO` 记录“文本可用、图片不可用”，不得输出为运行故障警告。自动测试日志写入 `wxbot_logs/tests/`，不得污染真实运营日志。日志降噪只处理预期内、已兜住、会高频重复的事件；真实故障必须逐次保留。

动态监听窗口的添加和关闭在 owner 内统一记录一条 `微信窗口耗时`，显示总耗时及排队、等待微信、实际操作三段时间。完成且低于 30 秒时用 `DEBUG` 只写本地文件，30 至 60 秒用 `INFO`，超过 60 秒或任意阶段失败用 `WARNING`；尚未进入 handler 的失败必须标记为“未开始”。业务层不得再包裹第二层总耗时日志，避免同一次操作重复记录。

### 任务与素材

定时消息、素材转发走统一时间模型。新增任务类面板时优先复用现有任务工作台 contract / storage / service。

非幂等动作在调用前持久化执行围栏。定时消息按“目标 × 内容”保存 `pending / inflight / done / failed / queued / uncertain`；好友申请真正提交只做一次；素材批次预写 `inflight`。进程中断后无法确认结果的一律进入 `uncertain` 或待确认，禁止自动重放。好友申请候选生成前必须重新计算 `duplicate_send_name`，并与 `send_name_unsearchable` 一起排除；`contact_key` 不能让微信的名称搜索具备同名消歧能力，禁止在无法唯一定位时自动提交。

普通语音、文件、转发和 quote 由 `core/message_store.py::SQLiteUIDeliveryJournal` 在 owner 已取得 wxautox4 全局锁、即将调用 handler 时写入同一数据库的 `ui_deliveries` 表；排队或等锁失败时 handler 尚未调用，不得提前写 `inflight / uncertain`。只有 handler 明确返回成功才写 `done`，返回 `False / None / 明确失败结果`、真实发送调用异常或启动时发现遗留 `inflight` 都收敛为 `uncertain`。唯一可释放已写入围栏的例外是 handler 明确抛出 `UIOutboundNotStarted`，表示监听子窗口最终未准备好且 `SendMsg / SendFiles / SendAudio / forward / quote` 均尚未调用；它不是任务取消：AI 回复 action 回到 `pending` 并按原投递 ID 自动重试，定时消息、群欢迎、新好友欢迎和素材转发则记录明确的“未发送”结果，不额外创建可能重复发送的重试队列。此时删除仍为 `inflight` 的 UI 围栏；围栏已完成、已是 `uncertain` 或无法确认释放时仍禁止重试。handler 失败结果落库后必须向调用方抛出，阻止外层换新投递 ID 自动重试。投递 ID 不按条数截断，素材转发还必须记录 `request_id / run_id / batch_id / targets`，同一业务批次结果未知时外层立即停止，禁止换一个随机 ID 自动再试。关键词、定时任务、新好友欢迎、quote 后续文字和 AI 拆分气泡都逐项提交；每项开始前复核会话或任务版本，新消息或配置变化可以取消尚未开始的剩余项；停止只阻止本进程继续提交，未进入微信处理器的回复保留为待恢复。不得把已完成、结果未知和尚未开始的多项合并成一个模糊结果，更不得把根本未开始的后续项一并冻结。

私聊和群聊恢复不再维护第二份待答 JSON。`chat_events` 保存入站事实和 60 分钟有效期，`reply_jobs` 绑定当前一次生成的回复计划，`delivery_actions` 保存每个气泡的 claim 边界。启动时，60 分钟内且未跨发送边界的旧任务只恢复其入站事实：删除旧回复计划、将事实重新置为 `pending`，再走当前的普通合并、路由、生成和版本校验；不复用旧 AI 文案、旧路由或旧 turn ID。全局扫描模式先用首次未读快照判断：有同会话未读的，等该会话扫描批次到达后先放回旧消息、再放入新消息；没有同会话未读的立即放回普通队列。扫描返回空批次时，也只能释放当前未读快照中已消失的会话，不能因一次空结果抢先回复仍显示未读的会话。这样旧消息与新消息始终走同一套合并规则，且启动不会为了恢复任务优先建监听窗口。任何遗留 `inflight` 动作转成 `uncertain`，同轮剩余气泡取消，禁止自动重发；已完成过部分气泡的剩余内容也不在重启后重建。明确跳过的图片、语音和暂停回复消息必须收敛为 `not_required`，不能留作下次启动待处理；仍等待微信转写的语音保持 `pending`。停止不取消尚未跨发送边界的回复任务；超过 60 分钟的入站事实自动过期并丢弃。当前进程内只有 SQLite 明确返回 `BUSY / LOCKED` 才自动恢复：业务入口按 `1 / 2 / 5 / 10 / 30 / 60s` 退避，协调器在 claim 前按 `30 / 60s` 低频尝试，均不超过原 60 分钟有效期；代码契约、数据冲突、状态跳转、结构损坏和其他数据库错误只失败一次并终结对应任务。真实微信调用一旦开始，失败或结果不明都转为 `uncertain`，不再自动重发。

owner 在真实微信动作前通过 `task_version_provider` 复核配置或任务定义真源；关键词必须读取账号级 `rules.json`，不能从已移除规则字段的全局配置计算版本。私聊和群聊关键词引用都只把首个文字动作改为 `quote`，群聊 @ 也只附加在该动作上；找不到原消息时可降级普通文字，真正调用后结果未知仍必须收敛为 `uncertain`。联系人目标保存 `contact_key`，执行前解析当前发送名；已失效、无法唯一解析或通讯录选择项缺少 `contact_key` 时拒绝执行。只有明确的自由输入目标允许按精确名称执行。好友申请提交前 claim 若因版本校验取消，使用 claim token 恢复为 `pending`；候选刷新必须继承活动 claim token，只有已经进入真实提交且结果未知时才保留 `uncertain`。

手动立即扫描和全量扫描只以当前运行 `WXBot.wx_id` 为账号真源，不读取或兼容面板请求中的历史 `wx_id`；响应必须返回实际运行账号，让页面同步切换。手动关系全量扫描是一个连续、不可抢占的 owner 独占事务：先回顶部，连续读取和滚动，连续 8 次无新增自然完成；中间不放行回复，也不允许手动停止。1000 次只作防无限循环保险，命中时必须标记 `partial`。heartbeat 只延长长事务整体截止线，单个底层 UI 调用卡死仍由 watchdog 恢复。

全量扫描每次 `roll_down()` 后直接读取下一屏，不恢复旧分片方案遗留的 1 秒等待；开始和结束回顶后各保留 1 秒稳定等待。自动短扫描看到 `full_scan_running=true` 时直接跳过；如果已在 owner 前等待，owner 返回后必须重新加载最新状态再合并，不能用排队前的旧 `runtime` 覆盖全量扫描完成状态。

最终生产压力使用 `tools/probe_production_acceptance.py` 只读观察。它从启动时的日志 EOF 开始计数，避免把单元测试旧日志混入证据；同时记录面板 HTTP、本机 `/runtime_health` 的机器人在线状态、10001-10999 的实际监听面板数、通讯录 worker 数、运行期间变更的关键 JSON、账号级 `message_store.sqlite3` 完整性和运行指标差值。默认 7200 秒及全部事件类别是自动门禁；正式采样间隔不得超过 5 秒，活动必须覆盖首尾桶且不能出现超过一个空桶的断层。每个 `WXBot` 实例生成独立 32 位 `runtime_id`，owner 排队、入站、通讯录批次和人工介入事件都携带该 ID；观察器只计入 `/runtime_health` 当前返回的唯一稳定实例，测试或旧实例日志不能拼成通过。缺事件、运行实例变化、机器人或 UI owner 任一采样点未运行、多个面板进程族/worker、结束时 worker 残留、面板不可达、持久化状态损坏或故障日志都会失败。报告不保存昵称、消息正文或正文哈希，只保留事件时间、日志文件名和字节偏移；`/runtime_health` 只允许本机访问，只在面板内机器人线程、UI owner 和非停止状态同时成立时返回 `bot_running=true`。即使自动门禁通过，错误窗口、真实重复/漏发，以及第 25 项通讯录批次内四类入站的接续时序仍必须人工复核。

定时消息内容模型是可选 `1` 条文案 + 最多 `9` 个本地文件，发送顺序固定为先文案、后文件。

素材转发里的 AI 文案已经统一成同一层。`AI自动转发` 仍是两段式链路：先判断当前最适合发哪条素材，再生成最终附加文案；不要把判断和文案生成混成一次模型调用。


## 高风险修改点

- 登录 / session。
- 微信监听注册、动态子窗口缓存和全局监听按需补窗。
- 消息回调分流顺序。
- 素材来源静默规则与普通消息路由的优先级。
- 发送前清洗、拆分多条和后续气泡间隔策略；不再设置首条回复延迟。
- outbound echo 过滤和私聊 `self` 手动接管判定。
- 回复轮数计数和超限结束语。
- 会话记忆提取、提案合并和保护规则。
- 私聊上下文补洞、history 组装顺序和 UI owner 排队边界。
- 定时任务 `next_fire_at` 推进、任务热更新和状态回写。
- 素材转发记录、进度记录和 AI pending 队列状态。
- 通讯录档案、身份校准、备注修复和手动目标名解析。
